## 0. なぜ作ったか

v1.0 以前も FB は開発を動かしていた (週次リキャップの発見プール方式・記録時の安心ヒント・肉じゃが・ギリシャ風サラダ)。ただ流れは「会話 → すぐ実装 → あとから ROADMAP に書く」で、次の4つが抜けていた。

1. **原文が残らない** — 何人が言ったか、どんな場面だったかを後から追えない
2. **1人の声で動く** — 件数と人数の区別が無い
3. **保留が待ち受けられていない** — ROADMAP の「今後の FB を見て判断」に、何が来たら動くかが書かれていない
4. **出したあとに戻していない** — 3層の「実ユーザー検証済」が埋まる経路が無い

## 1. 4層 + 戻りループ

```
Signal ──翻訳──▶ Problem ──仮説──▶ Story ──採用──▶ ROADMAP ──出荷──▶ 検証
(Notion)        (型で束ねる)      (1:n)        (PRD先行)            │
   ▲                                                                  │
   └──────── 根拠のテスターに聞き返す / 行動データで確かめる ◀────────┘
```

| 層 | 置き場所 | 単位 | 中身 | 次へ上げる条件 |
|---|---|---|---|---|
| **Signal** (FB-n) | Notion「FB Inbox」(非公開) | 1発言・1観察 | FB (テスターの言葉そのまま) / 日付 (登録日・自動) / 経路 / テスター (匿名コード) / 文脈 (そのとき何をしていたか) / 端末 / メモ (こちらの補足) | 週次トリアージで必ずどこかへ振り分ける |
| **Problem** (P-nnn) | [PROBLEMS.md](./PROBLEMS.md) | 困りごとの「型」 | 誰が・どの場面で・何に困るか (**解決策は書かない**) / 体験軸 / 根拠 FB と人数 / 深刻度 / 確信度 | §5 の目安を超えたら Story を立てる |
| **Story** (P-nnn-a, b…) | PROBLEMS.md の各 Problem の下 | 解決の仮説 | 「〜のとき、〜したい。そうすれば〜」/ 受け入れ条件 / 状態 (採用・保留・見送り) と理由 | 採用したら PRD を先に更新し、ROADMAP に載せる |
| **ROADMAP** | [ROADMAP.md](./ROADMAP.md) §3.0 | 既存のエントリ | エントリに `起点: P-nnn` を書く | 出荷で「コード有・到達可能」 |
| **検証** | Problem の状態 | — | 根拠テスターへの聞き返し or 行動データ | 解消を確かめたら「実ユーザー検証済」にして Problem を閉じる |

Story は別ファイルにせず Problem の下にぶら下げる。1つの困りごとに対して「採用した案・保留した案・見送った案」が並んで見えることが、ROADMAP の「当初案との差分」を書くときの材料になるため。

## 2. 守るルール

1. **原文と解釈を分ける。** Signal に「つまり〜」を書かない。解釈は Problem に書く
2. **要望は Problem に翻訳する。** 「〜機能が欲しい」は解決案。なぜ欲しいのかに戻す
3. **型で束ねる。** 1件の報告を直すのではなく、同じ型を全体から洗い出す (「肉じゃが」1件 → 和風おかず全体の着地穴)
4. **数えるのは件数ではなく人数。** テスターが少なく友人中心なので、声の大きい1人に引っ張られやすい
5. **不具合は別レーン。** Problem を通さず、すぐ直すほうへ回す (Signal は状態=不具合へ)
6. **ほめ言葉も残す。** 何を壊してはいけないかの根拠になる
7. **保留した案はトリガー付きで残す。** 新しい Signal は、まず既存の保留トリガーに当たるかを見る

## 3. 公開リポジトリのルール

**このリポジトリは PUBLIC。** テスターの名前・原文・連絡先はリポジトリに書かない。

- PROBLEMS.md に書くのは **FB 番号と、言い換えた要旨だけ**
- テスターは Notion 側で匿名コード (T01, T02…) にしておく。名前と匿名コードの対応表は Notion にも置かない (自分が覚えていれば足りる人数のうちは)
- **フォームのスクリーンショット欄には、体重や食事ログが写っていることがある。** 画像は Notion の外 (リポジトリ・コミット・PR) に出さない。Problem に書くときは、画面の内容を言葉で言い換える
- Claude がトリアージするときも同じ。Notion で読んだ原文をコミットに含めない

## 4. 経路

### 4.1 受け取る (いま来ている経路)

いまの FB は LINE と口頭が中心 (テスターが友人中心のため)。経路を変えてもらうより、**受け取った側が30秒で Signal に入れられること**を優先する。

| 経路 | 入れ方 |
|---|---|
| LINE | メッセージをコピー → Notion アプリで FB Inbox に新規 → 原文に貼る。経路=LINE |
| 口頭 | 聞いたその日のうちに、覚えている言い回しのまま書く。経路=口頭。その場で「そのとき何してた？」を1つ聞いておくと文脈が埋まる |
| 検索のミスログ | 「見つからなかった食品」の共有は [SEARCH_SPEC.md](./SEARCH_SPEC.md) / 検索ベンチマークの流れで処理する。Signal には「まとめて1行」で入れれば足りる |

### 4.2 こちらから用意する

友人は自分からは言わないし、言うときはほめがち。待つだけでは困りごとが集まらないので、こちらから取りにいく経路を足す。

| 経路 | 状態 | 内容 |
|---|---|---|
| **A. 定期の問いかけ** | 提案 | 2週に1回、LINE で同じ1問を投げる。**意見ではなく最近の具体的な出来事を聞く** (「使いやすい？」は聞かない)。例:「この2週間で、記録しなかった食事はあった？ そのとき何があった？」「最後に記録したとき、手が止まったところはあった？」 |
| **B. Notion フォーム** | 公開済・アプリ導線は次の配布ビルドから (2026-10-24) | FB Inbox の「テスター向けフォーム」ビュー。匿名で、同じデータベースに直接入るので書き写しが要らない。LINE では言いにくいこと・長く書きたいこと向け。アプリの 設定 > フィードバック「不具合・要望を送る」から開く (PRD v1.16 §6.8。Google フォーム案を置き換えた)。LINE でリンクを直接送ってもよい。フォームから来た行は経路が空なので、トリアージで「フォーム」を付ける |
| **C. 出荷後の聞き返し** | 運用開始 | 根拠 FB のテスターに「直したので試してみて」と送る。検証になるうえ、「言えば直る」と伝わることで次の FB が出やすくなる |
| 見送り: テスター全員の LINE グループ | — | 他人の声に引っ張られる・友人同士だと言いにくい。人数が増えてから再検討 |
| 後回し: アプリ内のその場 FB | — | Layer 2 (自前の受け口) の範囲 |

## 5. 優先度の目安

Problem に次の4つを書き、Story を立てるかを決める。点数化はしない (人数が少ないうちは点数が誤差に埋もれる)。

- **人数** — 何人が同じ型の困りごとを言ったか
- **深刻度** — 止まる (記録をやめた・諦めた) > 迷う (手が止まった・調べに行った) > 不満 (使えるが気になる)
- **体験軸** — EXPERIENCE_DEPTH の ①〜⑥。①記録 と ⑤継続 は北極星に直結する
- **確信度** — 発言1人 < 複数人 < 行動データでも確認

**目安**: 「止まる」かつ ①⑤ に当たるものは1人でも Story を立てる。それ以外は2人以上、または行動データで裏が取れてから。

## 6. 運用リズム

| 頻度 | やること | 時間 |
|---|---|---|
| 随時 | Signal に入れるだけ。解釈しない | 30秒 |
| 週1 | トリアージ (§7)。「未整理」ビューを空にする / 保留トリガーと照合する / 検証待ちを聞きに行く | 30分 |
| 月1 | ROADMAP の月次レビュー (§8) に、開いている Problem を人数・深刻度の順で持ち込む | 既存のレビューに相乗り |

## 7. 週次トリアージの手順

> **自動の下書き (2026-10-24〜)**: 毎週月曜 8:30 に定期実行 (`weekly-fb-triage`) が 1〜3 の下書きを Notion の非公開ページ「週次トリアージ YYYY-MM-DD」に作り、通知を出す。**FB Inbox の行も PROBLEMS.md も書き換えない** (4 は人が確認してから)。Claude アプリが開いている間に動き、閉じていれば次に開いたとき実行される。未整理が0件の週は何もしない。確定は「FBトリアージを確定して」と頼む

Claude に「FB トリアージして」と頼めば、1〜3 の下書きまでを出す。4 はユーザーの確認のあとで行う。

1. Notion「Hachibu フィードバック」> FB Inbox の **状態=未整理** の行を読む
2. 各行について、次のどれかを提案する
   - 既存の Problem につなぐ (人数が増えるか、テスターが同じなら件数だけ増える)
   - 既存の **保留 Story のトリガーに当たる** → その Story を再検討に上げる
   - 新しい Problem を立てる (同じ型が他に無いかも洗い出す)
   - 不具合へ / 対象外
3. 出荷済みで検証待ちの Problem について、聞き返す相手 (FB 番号から) と聞き方を挙げる
4. 確認後、Notion の 状態・Problem を更新し、PROBLEMS.md の根拠・人数・状態を更新する。新しい P 番号は Notion の Problem 欄の選択肢にも足す

## 8. ROADMAP との接続

- Story を採用したら、**PRD を先に更新** (CLAUDE.md の規約どおり) → ROADMAP §3.0 にエントリを書き、`起点: P-nnn` を添える
- ROADMAP 側で「今後の FB を見て判断」と書くときは、PROBLEMS.md に保留 Story として**トリガー付きで**残す
- 出荷したら Problem の状態を「検証待ち」にする。聞き返しで解消を確かめたら ROADMAP の該当エントリも「実ユーザー検証済」に更新する
