## 1. 全体方針

### 1.1 北極星
オンボーディング完了後 **24時間以内の初回食事ログ完了率** (PRD §10.1)。
Next 期以降は **D7 / D30 リテンション** および **週次アクティブ率** をセカンダリ指標に追加する。

### 1.2 5スイムレーン
| レーン | テーマ | 狙い |
|---|---|---|
| **A. 食事入力** | 入力経路の拡張 (検索 / バーコード / AI) | "記録できなかった" を減らす。`quick_log_unfound_event` の解消 |
| **B. 活動連携** | Health Connect / 動的目標 | TDEE 精度向上、"今日は動いた分食べていい" の納得感 |
| **C. 継続性** | リマインダー / ストリーク / レビュー通知 | 北極星KPIの次層 (D7/D30) を底上げ |
| **D. AI / コーチング** | AI レビュー / 動的ペース提案 / 写真認識 | 入力摩擦の削減 + "次の一手" の提示 |
| **E. 横断** | KPI整備 / マネタイズ / プラットフォーム拡張 | 単発機能ではなく土台寄り、後段の差別化に効く |

### 1.3 ベンチマーク方針 (v1.6)
食事入力レーンは **「あすけん主軸 + 解釈A (最後の砦としての検索)」** で進める (PRD §6.5.0)。DB件数で勝負せず、9ボタン × Identity ツリー × 自動学習というコア体験の軽さを毀損しない。

  - アーキテクチャ: **ダムウィジェット + pending queue + アプリ側 resolveLog**。ウィジェットはマクロ計算・整合性判断を一切持たず、タップ時に共有ストア (Android DataStore / SharedPreferences) の pending queue へ JSON 追記するのみ。アプリ起動・フォアグラウンド復帰時に queue を drain → 既存 `resolveLog` で確定 → FoodLog 追加
  - ボタン供給: `pickInitialDraft` 上位N件 (履歴が浅い場合はシステムデフォルトで補完)。ラベルは必ずデフォルト量つき (例「ごはん 1杯」) で即記録の内容を明示
  - undo: 記録直後にウィジェット上で「記録しました ↩取消」。drain前は queue から削除 / drain後は該当ログ削除
  - サイズ別:
    - **1×1**: カロリーリング (摂取/目標、中央に残kcal)。タップ→アプリホーム。リングの分母は **targetCalories + 当日の運動消費分** (net で「あと食べられる量」を表示)
    - **2×2**: クイックログ4ボタン (即記録 + undo)
    - **4×2**: 左にカロリーリング + 右にクイックログ4ボタン (記録 + 把握ハイブリッド)
    - **3×3**: クイックログ9ボタングリッド (上部に合計/リング)。パワーユーザー向け
  - 実装: Android = Kotlin Glance + 共有ストア + pending queue。iOS (WidgetKit/Swift) は **Later** に分離 (UI・配線は別実装、pending queue の JSON 契約 と drain ロジックのみ流用)
  - 依存: リング分母は既存 `adjustedTargetKcal` (係数 + 運動ログ) で成立し、ブロッカーなし。動的TDEE 差分方式 (B レーン) が入れば「大きく動いた日」も自動でリングに反映される (任意の上乗せ)

### B. 活動連携 (★ ユーザー要望②の本丸)

- **Apple Health / Health Connect 連携 (体重・体脂肪 自動取得)**
  - PRD §6.6.3 既述の「将来検討」を実装フェーズへ
  - WeightEntry / BodyFatEntry スキーマは既に分離済み (PRD §8.2)
- **歩数 / アクティブエネルギーの自動取得**
- **動的TDEE: 活動量による日次kcal目標の補正 (差分方式)**
  - 方針確定 (2026-06-04): 歩数/activeKcal を**全額加算しない**。活動係数 (1.2〜1.725) は「日常移動込みの1日全体」を表す標準PAL値であり、通勤・買い物等の日常分は既に係数に織り込まれている。歩数を全額足すと二重計上になる。
  - **差分方式**: 当日活動が「係数が想定する基準活動量」を**明確に超えた分だけ**目標に上乗せ。
    - 普段の日 → 基準前後 → 加算ほぼゼロ → 目標が安定 (フラフラしない)
    - 登山・ディズニー・旅行等で大きく動いた日 → 超過分を「今日 +○○kcal の余裕」として加算
    - スマホ非携帯で取りこぼす仕事中の動きは係数側で担保 → 歩数依存しない
    - 歩数の日常的な誤差はしきい値で吸収 → 大きく動いた日だけ効く
  - 設計詳細は **PRD §6.4.3** で定義:
    1. レベル別 基準活動量 (基準歩数 or 基準activeKcal)
    2. 超過分の kcal 換算式
    3. 日次キャップ (異常値/GPSノイズ吸収)
    4. **運動ログとの二重計上調停**: ExerciseLog 記録済みの運動も歩数/activeKcal に含まれるため、「歩数加算 と 運動ログ加算 の大きい方を採る」等の調停が必須
  - **UX**: 「今日 +180 kcal の余裕」のように見せる (kcal目標の置き換えではない)
  - **係数見直しサジェスト (下げ方向のみ・Later)**: 差分方式が「動いた日」を日次で自動補正するため、係数を**上げる**提案は役割が被り不要。一方で差分方式は基準を**下回る**分はマイナス補正しないため、「動き回る仕事を選んだが実測 activeKcal が継続的に基準を大きく下回る」= 目標過大ケースのみ救えない。これに限り、控えめな**下げ提案**を中立トーンで出す (Later、優先度低)
  - **【検討バックログ】ベースTDEEの活動傾向ベース自動補正 / adaptive TDEE (2026-06-05 追加・要設計)**: 上記「日次の差分ボーナス」とは別レイヤーで、**ベースTDEE (係数そのもの)** を継続的な実測から補正する案。判断材料として2方式を比較検討する:
    - (a) **歩数/activeKcal の一定期間平均** から係数の妥当性を判定 → 上記「下げサジェスト」に集約済み。上げ方向は差分方式と二重になるため不採用。
    - (b) **体重トレンドからの逆算 (adaptive TDEE)**: 実測の増減ペース vs 予測ペースの乖離から真のTDEEを推定。歩数より精度が高く「なぜ痩せ(ら)れないか」に直結。ただし体重記録の継続が前提・推定の安定化 (移動平均・外れ値除去) が必要。
    - **方針メモ**: 完全自動で目標を毎日いじるとブレて体験が悪い → ユーザー承認を挟むサジェスト型が基本。優先度は (b) > (a)。着手は Later、まず差分方式の運用データを見てから。
  - **PRD更新**: §6.4.3 新設 / §4.1 In Scope境界 / §10.2 KPI に反映
