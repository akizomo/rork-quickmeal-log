## 1. Problem Statement

### 1.1 現状
MVP 段階の Quick Log は **9 ボタン × Identity ツリー × 自動学習** の3段構造で、9バケットのいずれかに Identity を抽象化して収録している。Identity 全件検索バーはコードとして実装済みだが、UI からは非表示になっている (PRD §4.2)。

### 1.2 解決したい問題
- 9 ボタン経由でも長押し階層展開でも目的 Identity に届かないケースが発生する (例: ブランド指定したい / 特殊な料理名で探したい / コンビニ商品名で直接検索したい)
- このフォールバック手段がないと「あすけんなら載っているのに、ここにはない」という体感を生み、競合 (あすけん主軸) に対する離脱要因になる
- 一方で検索を主導線化すると、9ボタン × 自動学習というコア体験の軽さ (PRD §6.5.0 解釈A) を毀損するリスクがある

### 1.3 解決方針 (PRD v1.6 で確定)
- **解釈A**: 検索バーは「ボタン+長押しで届かなかった時の最後の砦」として再有効化する
- **DB件数で勝負しない**: 1,000〜3,000 Identity + ブランドチップ数百〜千件で十分
- **コア導線は変えない**: 9 ボタンが主導線、検索バーはフォールバック

### 1.4 出荷後の実測診断 (2026-08-10)

Phase 1 出荷後、「ポテトサラダで検索したのに出ない」という実利用の指摘を起点に `searchIdentitiesFuzzy()` を実測した。**ポテトサラダは DB に2箇所存在し、うち1つはデフォルト値**であるにもかかわらずヒットしない。

```
ポテトサラダ → Style:potato/salad_mayo, Attr:side_creamy/potato_salad (isDefault)
実際の検索結果 → 「サラダ・生野菜」「サラダチキン」(どちらも誤り)
```

#### 原因① 検索対象が Identity 層のみ — DB の 6割が不可視

| 層 | 件数 | 検索可能 |
|---|---|---|
| Identity | 124 | ✅ |
| searchTags | 83 | ✅ |
| **Attribute** | **243** | ❌ |
| **Style** | **50** | ❌ |
| 計 | 500 | **207 (41%)** |

ユーザーが口にする名前 (ポテトサラダ / 親子丼 / キムチ / コロッケ / メンチカツ / 唐揚げ) は **Attribute 層に集中している**。本仕様書 v0.3 までが全編「Identity を検索する」前提で書かれていたことが、この盲点の原因。

実測: `親子丼`→0件 (`gyudon_class/oyakodon` が存在), `キムチ`→0件 (`pickles/kimchi`), `コロッケ`→0件 (`fried_main/korokke`), `コールスロー`→0件 (`side_creamy/coleslaw`)。

#### 原因② 誤ヒットが正しい逃げ道を塞ぐ

カテゴリヒントは `results.length > 0` で抑制される (`SearchSheet.tsx`)。`ポテトサラダ` は無関係な「サラダチキン」が返るため0件扱いにならず、**ヒントも出ない**。純粋な0件より体験が悪いという逆転が起きている。

さらに深刻なのは、診断ログ (`recordSearchMissEvent`) も「ヒットあり」として破棄されること。**この失敗は KPI に一切残らない** — §5.4.3 の0件クエリ運用ループが機能しない前提条件になっている。

#### 原因③ bigram類似度の誤爆

クエリ側の bigram 数でのみ除算する非対称な実装 (`identity-search.ts`) のため、短いクエリで暴走する。

| クエリ | 誤ヒット | 原因 |
|---|---|---|
| `ミネストローネ` | いちご | — |
| `スコーン` | とうもろこし, ポップコーン | — |
| `スタバ` | パスタ | {すた,たば} vs {ぱす,すた} = 0.5 ≥ 閾値0.4 |
| `ドリア` | ジュース, シリアル, プロテイン | — |

#### DB非収録食品の実測 (一般的な料理50品)

| 結果 | 件数 |
|---|---|
| DB に収録済 | 16 |
| DB 非収録 | **34** |
| └ うち **手がかりが一切出ない** | **23** |
| └ うち偶然それらしい候補が出る | 11 |

偶然当たっている11件 (`ビーフシチュー`→カレー・シチュー系, `肉じゃが`→じゃがいも・里芋) は「料理名に DB 収録語が文字列として含まれていた」偶然であり、**原理がない**。

## 2. User Stories

### 2.1 Primary
- **U1**: ユーザーとして、9 ボタンで思った Identity が見つからないとき、画面上部の検索バーから商品名・料理名・食材名で直接検索したい (例: 「サラダチキン」「カフェラテ」「鶏むね」)
- **U2**: ユーザーとして、ひらがな・カタカナ・ローマ字のどれで入力しても同じ結果が得られたい (例: 「ぶろっこりー」「ブロッコリー」「broccoli」)
- **U3**: ユーザーとして、よく検索する Identity は次回検索時に上位に表示されたい
- **U4**: ユーザーとして、検索結果がない場合、何ができるか (リクエスト送信 / カスタム登録) を提示されたい

### 2.2 Secondary
- **U5**: ユーザーとして、検索結果から選んだ後は通常の Quick Log と同じフロー (量入力 → 確定) で記録できたい
- **U6**: ユーザーとして、検索バーを閉じれば 9 ボタン主導線に戻れたい (検索を主役にしない)
- **U7**: ユーザーとして、Identity DBにない食事を食べたとき、kcalと任意でPFCを直接数値入力して記録したい。検索シートを開いた画面内から動線を増やさずアクセスできたい

### 3.1 Must Have (Next での確定実装範囲)

> 検索ロジックも `searchIdentities()` ではなく `expo/utils/identity-search.ts` の `searchIdentitiesFuzzy()` (正規化 + bigram類似度) を使う。
> 旧 `IdentitySearchBar.tsx` / `searchIdentities()` は参照ゼロとなり削除済。以下は当初仕様として保持する。

- Quick Log 画面上部に検索バーを再配置
- プレースホルダー: 「食材・料理・ブランド名で検索」
- ~~既存実装 (`expo/components/IdentitySearchBar.tsx`) の構造を踏襲~~
  - debounce: 200ms
  - 結果表示: 上限 8件 (現行の `MAX_RESULTS` を維持)
  - 選択時挙動: 該当 Identity の primary home バケットで `IdentityLogSheet` を pre-select 状態で開く

#### F2. 検索ロジック強化

##### F2-0. 検索単位を `SearchEntry` に再定義 (v0.4 新規・最優先)

> **v0.3 までの仕様の盲点。** 本節以外の全記述が「Identity を検索する」前提で書かれていたが、ユーザーが実際に入力する語の多くは Attribute / Style 層にある (§1.4 原因①)。

検索インデックスの単位を `Identity` から **「記録可能な状態」** に変更する:

```ts
type SearchEntry = {
  identity: Identity;
  attribute?: AttributeOption;  // 例: side_creamy + potato_salad
  style?: StyleOption;
};
```

- `ポテトサラダ` は `side_creamy + potato_salad` という **1つの引ける実体**になる
- 選択時は Attribute まで pre-fill した状態で `IdentityLogSheet` を開く
  - **前提**: `openIdentityLogSheet()` (`app-state-provider.tsx`) が現状 `identityId` までしか受け取らないため、`attributeKey` / `styleKey` を受け取れるよう拡張が必要
- 検索面が **207 → 500** に増える

**表示方針: フラット表示** (2026-08-10 決定)
- 同一 Identity 配下の Attribute が複数ヒットしても畳まず、そのまま並べる
  - 例: `唐揚げ` → 唐揚げ定食 / 唐揚げ弁当 / 唐揚げ(もも) / 唐揚げ(むね) の4件
- 理由: 4件程度なら一覧性を損なわず、「ちゃんと当てた」という体感が畳み表示より強い
- **ただしランキング (F3) が効いていることが前提** — 頻度学習で使う順に並ぶこと
- **同一 Identity からの上限は4件**とし、それ以上は打ち切る (実測の最悪ケース: `揚げ` で8件、`定食`/`かつ` で6件。MAX_RESULTS=8 を単一 Identity が占有するのを防ぐ)

**インデックス除外: 文脈依存ラベル**
Attribute ラベルには単独で意味をなさない修飾語が存在するため、standalone のエントリにしない。

| ラベル | 出現 Identity 数 | 判定 |
|---|---|---|
| `普通` | 5 (noodle_pasta, milk, chocolate, bibimbap, burger) | 除外 |
| `加糖` / `皮なし` / `皮あり` / `水煮` / `油漬` / `かけ` / `鮭` | 各2 | 個別判断 |

- 判定則: **同一ラベルが3つ以上の Identity に出現する場合は修飾語とみなし standalone 検索から除外**する (親 Identity 名との複合形 `牛乳 普通` としてのみインデックス)
- 実測では全232ラベル中、重複は8件のみ。除外対象は極めて限定的

##### F2-1. 正規化・マッチング
- **正規化** (§5.1 詳細): 入力クエリと Identity の検索対象文字列を揃える
  - 全角 ↔ 半角 / ひらがな ↔ カタカナ / 大文字 ↔ 小文字 / 長音除去
  - ローマ字 → ひらがな (訓令式 / ヘボン式 両対応、§5.5 内製辞書)
- **同義語辞書**: Identity ごとに `searchTags` で同義語・英語名・口語表記を保持 (§5.4)
- **マッチングスコア** (優先度順):
  1. 完全一致 (score 4)
  2. 前方一致 / クエリが先頭3文字以上と一致 (score 3)
  3. 部分一致 (score 2)
  4. bigram重複率 ≥ 40% のファジーマッチ (score 1〜2) — 曖昧な入力でも候補を返す
- **「0件を出さない」設計**: ユーザーは食品名を正確に知らないまま検索する。score > 0.5 のものをすべて候補として出し、スコア順に並べる。完全一致がなくてもファジー候補を優先して見せる
- **英語クエリ対応**: `searchTags` に英語名を必須収録し、`pizza`→×ではなく `pizza`→(0件+カテゴリヒント) で補完

#### F3. ランキング (頻度学習統合)
- 検索結果の並びは以下を加味:
  1. マッチングスコア (F2 の score値)
  2. ユーザー固有の選択頻度 (§6.5.1 自動学習と統合)
  3. グローバルな出現頻度 (Identity マスター側)
- 同点時は Identity の primary home バケット順 (タブ並び順と整合)

#### F4. 量入力フロー
- 検索結果をタップ → IdentityLogSheet を開く (現行挙動維持)
- 量入力は Quick Log と同じ `AmountSpec` を使用
- ブランド指定がある Identity は `brandChips` を提示 (PRD §13.1 P2-S4 と統合)

#### F5. 着地保証モデル — 「0件を出さない」4層 (v0.4 全面改訂)

> **原則の転換 (v0.4)**: 未知の食品に対する0件は「正常なフォールバック」ではなく **設計の失敗** とみなす。
> このアプリの前提は PFC 収束であり、`ケバブ` を「脂あり肉魚」として記録すれば十分である
> ([docs/VOICE.md](./VOICE.md)「Roughly is enough.」)。**未知の食品はカテゴリで着地するのが正常系**であり、
> UI はそれを謝罪せず提示する。

| 層 | 対象 | 手段 | 例 |
|---|---|---|---|
| **1. 語の一致** | DB 収録語 | `SearchEntry` (F2-0) | ポテトサラダ / 親子丼 / キムチ |
| **2. 主辞の一致** | 複合語で主辞が DB 内 | **主辞辞書** (§5.4.5) | ハムカツ→揚げもの単品 / ひじき煮→煮物 / だし巻き卵→卵 |
| **3. 語彙の一致** | 主辞を持たない単一語 | **料理名辞書** (§5.4.6) | フォー→麺 / ケバブ→肉 / リゾット→ごはん |
| **4. 最終着地** | 完全未知 | カテゴリ選択の常時提示 | 「どのカテゴリで記録しますか」 |

**層2・3 が現状まったく存在しない部分**であり、§1.4 の「手がかりゼロ23件」の主因。

##### 表示の階層化 (確信度で分離する)

誤ヒット自体は害ではない。**無言で1位に置くことが害**である (§1.4 原因②)。ラベルで隔離する:

```
┌──────────────────────────────┐
│ ポテトサラダ          🥗 野菜・汁物   │  ← 層1: 確実。無言で出す
├──────────────────────────────┤
│ もしかして                        │  ← 層2/3: ラベルを付けて隔離
│ マカロニサラダ / コールスロー          │
├──────────────────────────────┤
│ このカテゴリかも                     │  ← 層4: 常時表示 (ヒット有無を問わない)
│ 🥗 野菜・汁物   🍚 ごはんパン麺        │
└──────────────────────────────┘
```

- **カテゴリチップは常時表示**に変更する (v0.3 までは0件時のみ)。誤ヒットが逃げ道を塞ぐ構造 (§1.4 原因②) の解消
- 層1のヒットが1件でもあれば、層2は「もしかして」見出しの下にのみ置く
- 常設フッター「数値で入力する」は全状態で表示 (変更なし)

##### 診断イベントの発火条件 (重要)

`recordSearchMissEvent` / `quick_log_unfound_event` は **層1のヒット有無**で判定する。
層2/3/4 でしか着地しなかったクエリは **miss として記録する** — これが §5.4.7 の辞書育成ループの入力になる。

> v0.3 の実装は「何かヒットしたか」で判定していたため、`ミネストローネ`→`いちご` のような誤ヒットが
> miss を握り潰していた。**辞書を育てる前提条件として、この修正が先行して必要**。

#### F5a. カテゴリ推定 (層4)
- クエリをキーワード辞書 (`categoryHints`) と照合し、関連カテゴリを最大4件推定する
- 辞書は `searchTags` と同じ正規化 (§5.1) を適用してマッチング
- 例: `pizza` → 主食 / `milk` → 乳·大豆 / `chocolate` → おやつ甘飲 / `なすび` → 野菜
- **推定不能な場合でも空にしない**: 頻度学習上位のバケット、それも無ければ9バケット全件を提示し、
  「数値で入力する」に落ちる前に必ずワンクッションを置く (層4の着地保証)

#### F_direct. 数値直接入力 (使い捨て記録)
- **入口**: 検索シートの**常設フッター**に「数値で入力する」リンクを常時表示。動線を1本に集約するため、9ボタン画面には独立した入口を設けない
- **フィールド**:
  | フィールド | 必須 | 備考 |
  |---|---|---|
  | 名前 | 任意 | 履歴表示用の自由テキスト。未入力時は「カスタム食品」と表示 |
  | kcal | **必須** | 整数のみ。0は不可 |
  | タンパク質 (g) | 任意 | 未入力は記録上 null (統計グラフでは目標比率から自動按分) |
  | 脂質 (g) | 任意 | 同上 |
  | 炭水化物 (g) | 任意 | 同上 |
- **再利用**: なし。記録は通常の食事ログと同じ `FoodLog` エントリとして保存されるが、Identity DBには追加しない (カスタム食品DB・再利用は P2-S7 で別途)
- **UI**: `BottomSheet` で開く。フィールドは `NumberField` コンポーネントを使用。確定ボタンタップ → ログ記録 → シートを閉じてホームへ戻る

## 5. 検索ロジック詳細

### 5.1 正規化パイプライン

**実装位置:** `expo/utils/identity-normalize.ts` (新規)。検索クエリ側と Identity 側 (起動時1回) の両方を同じ関数に通す。

#### 5.1.1 正規化ステップ (順序固定)

| 順 | ステップ | 入出力例 | 実装ノート |
|---|---|---|---|
| 1 | `trim()` | `"  チキン  "` → `"チキン"` | 標準 |
| 2 | **NFKC 正規化** (全角英数記号 → 半角、合成文字統一) | `"Ｂｒｏｃｃｏｌｉ１"` → `"Broccoli1"` | `String.prototype.normalize('NFKC')` |
| 3 | `toLowerCase()` (en-US ロケール) | `"Broccoli"` → `"broccoli"` | 標準 |
| 4 | **カタカナ→ひらがな** | `"ブロッコリー"` → `"ぶろっこりー"` | コードポイント計算 (`0x30A1〜0x30F6` → `0x3041〜0x3096`、`-0x60`) |
| 5 | **ローマ字→ひらがな** | `"burokkori"` → `"ぶろっこり"` | 内製辞書 (§5.5)、最長一致でトークナイズ |
| 6 | **長音/促音/拗音の正規化** (検索容易化) | `"ぶろっこりー"` → `"ぶろっこり"` | 長音 `ー` 除去、または直前文字の母音に展開 |

**設計原則:**
- **失敗時は止めない**: 各ステップは例外を投げず、不正入力時は前段の結果をそのまま返す (最低限 trim + lowercase は通過する設計)
- **冪等性**: 正規化済みの文字列に再適用しても結果が変わらない
- **検索クエリ側と Identity 側で同一関数を使う**: 二重実装による乖離を防ぐ

#### 5.1.2 長音 (`ー`) の扱い

- **searchTags 側**: 元表記 + 長音除去版の **両方** をインデックスに登録
  - 例: `"ぶろっこりー"` と `"ぶろっこり"` の両方を保持
- **クエリ側**: 長音を残したまま正規化 (前方一致で両方ヒット可能)

これにより、ユーザーが `"ブロッコリ"` (長音省略) で検索しても `"ブロッコリー"` Identity がヒットする。

#### 5.1.3 想定挙動 (受け入れテストの種)

| ID | クエリ | 期待ヒット |

| T1 | `BROCCOLI` | broccoli Identity (label: ブロッコリー) |
| T2 | `ぶろっこりー` | 同上 |
| T3 | `ﾌﾞﾛｯｺﾘｰ` (半角カナ) | 同上 |
| T4 | `burokkori` | 同上 |

| T6 | `さけ` | 同上 (ひらがな searchTags) |

### 5.2 マッチング (v0.4 改訂)

- 前方一致: スコア ×3
- 部分一致: スコア ×1
- `searchTags` ヒット: スコア ×2
- 表示名ヒット: スコア ×2

#### 5.2.1 bigram類似度の扱い — 主要結果から隔離する

実測 (§1.4 原因③) により、現行の bigram 類似度は **意味的に無関係な候補を主要結果の1位に置く**ことが確認された (`ミネストローネ`→`いちご`)。原因は2つ:

1. **非対称な除算**: クエリ側の bigram 数でのみ割るため、短いクエリのスコアが不当に高くなる
2. **形態素境界の無視**: 文字単位のため `スコー|ン` と `ポップコー|ン` が繋がる

**方針:**
- 層1 (確実なヒット) には bigram 類似度を**使わない**。完全一致 / 前方一致 / 部分一致のみ
- bigram は層2 (「もしかして」) 専用に降格する

> **実装 (2026-08-11) で対称化した。** `diceSimilarity()` (`2 × 共通bigram数 / (|q|の bigram数 + |target|の bigram数)`)
> を層2専用に新設し、非対称な旧 `bigramSimilarity()` は層4 (このカテゴリかも、§F5a) 専用として残した — 層4 は
> 「何も出さないよりは緩く出す」が設計意図の最終フォールバックのため、あえて非対称のままにしている。
>
> **対称化だけでは不十分だった点**: target が短い (bigram が1個しかない) と、その1個が一致しただけで
> Dice係数が不当に高くなる新種の誤爆が発生した (`グラタン`→`タン`、`たい焼き`→`焼き`単体)。substring
> と同様に `target.length ≥ 3` を bigram/Dice の適用条件に追加して解消した。
>
> **残存する既知の限界**: `スコーン` → `とうもろこし` (識別子 corn の `searchTags: ['コーン缶']` 経由、
> Dice値がちょうど閾値0.4) のような境界線上の誤爆が1件残る。閾値を0.45に上げると解消するが、
> `ビーフシチュー`→`シチュー`・`ラーメン`→`そうめん` 等の正当な近似候補も同じ境界に位置しており道連れで
> 失われるため、この trade-off では閾値を上げない判断とした。
- 除算を対称化する (Dice 係数: `2 × 共通 / (|q| + |t|)`) 。閾値は再チューニングが必要
- 層2・3 が機能すれば bigram の役目はほぼ無くなる。**Phase 2 完了時点で廃止を再検討する**

#### 5.2.2 主辞マッチの実装則 (層2)

「日本語の料理名は末尾が主辞」という規則性を使う。ただし**文字列の末尾一致は禁止** — 実測で形態素境界を越えた誤爆が多発した:

| クエリ | 文字末尾一致の結果 | 問題 |
|---|---|---|
| グラタン | 牛タン | `グラ\|タン` vs `牛\|タン` |
| スコーン | ポップコーン | `スコー\|ン` |
| たい焼き | 目玉焼き / 雑炊・鍋焼き | たい焼きは菓子 |
| シーザーサラダ | ポテトサラダ | 葉物 vs いも・マヨ (PFC が異なる) |

**規則: 主辞は「§5.4.5 の主辞辞書に登録された語」でなければならない。**
- クエリが登録主辞で終わり、かつ残りが1文字以上ある場合のみ層2マッチとする
- `タン` は主辞辞書に無いため `グラタン` は誤爆しない
- 主辞は**表層文字列ではなくバケット/Identity にマップする** (辞書が対応関係を持つ)

この規則により実測で正しく解決するもの: `ハムカツ`→揚げもの単品 / `ビーフシチュー`→カレー・シチュー系 / `ハヤシライス`→カレーライス・オムライス / `ひじき煮`・`筑前煮`・`もつ煮`→煮物 / `だし巻き卵`→卵

### 5.3 ランキング式

```
finalScore = matchScore × (1 + userFreqWeight × log(1 + userSelectCount))
                       × (1 + globalFreqWeight × log(1 + globalSelectCount))
```

- `userFreqWeight`: 0.5 (ユーザー個別の頻度を中程度に重視)
- `globalFreqWeight`: 0.2 (新規ユーザーへのフォールバック)
- 重みは A/B テスト可能な定数として実装

> **実装 (2026-08-10) では global 項を割愛した。** この app はローカル専用でユーザー
> 横断の集計基盤 (Analytics バックエンド) を持たないため、`globalSelectCount` を
> 埋めるデータ源が存在しない。捏造した固定値を入れるより、明示的に0として省略する
> 方が誠実と判断した。バックエンド計装が入った時点で追加を検討する。
>
> **頻度は「層内の並び順」にのみ影響させ、層 (confident/maybe) の判定には使わない。**
> bigram一致 (層2) が選択頻度だけで層1相当に格上げされると、「確信度で分離する」
> という設計原則 (§F5) が崩れるため。詳細は P4 実装ノート参照。

### 5.4 語彙 (v0.4 で3ソースに拡張)

> **v0.4 の中心的な方針転換: 未収録食品は「DB拡張」ではなく「語彙拡張」で解く。**
>
> `ケバブ` に専用 Identity は不要 — 「脂あり肉魚」に着地すれば PFC 収束の要件を満たす。
> これは §1.3「**DB件数で勝負しない**」の直接的な帰結である。Identity は 1,000〜3,000 のまま据え置き、
> 語彙のみを数百〜千件育てることで「あすけんなら載っているのに」という体感を解消する。
>
> | | データ拡張 (Identity追加) | 語彙拡張 (辞書追加) |
> |---|---|---|
> | コスト | 重い (PFC設計・amount・addon の設計が必要) | 軽い (語→バケットの1行) |
> | PFC設計への影響 | あり (バケットのクラスタが崩れうる) | なし |
> | 育て方 | 設計レビューが必要 | 0件クエリログから機械的に追加可能 |
>
> **v0.4 では後者を主軸に置く。**

| ソース | 単位 | 責務 | §  |
|---|---|---|---|
| `Identity.searchTags` | Identity / Attribute | 同義語・表記ゆれ・英語名 | 5.4.1〜5.4.4 |
| **主辞辞書** | 語 → バケット/Identity | 複合語の末尾主辞を解決 (層2) | 5.4.5 |
| **料理名辞書** | 語 → バケット | 主辞を持たない単一語を解決 (層3) | 5.4.6 |

#### 5.4.1 同義語の単一情報源 (Single Source of Truth)

**決定: `Identity.searchTags: string[]` を正とする (新規辞書ファイルは作らない)**

理由:
- 既に Identity 単位で散在しており、Identity 追加と同じ PR で同義語が増える運用が成立しやすい
- `Record<IdentityId, string[]>` 別ファイル化は二重管理になり、Identity 削除時の整合担保が面倒
- `searchTags` の TS 型 (`string[]`) はそのままで運用負荷ゼロ

> v0.1 の §5.4 で提案していた `expo/constants/identity/synonyms.ts` 案は **撤回**。

#### 5.4.2 searchTags に格納する情報の必須/推奨/任意

| 種別 | 必須/推奨 | 例 (Identity: ブロッコリー) | 備考 |
|---|---|---|---|
| **表示名カナ表記** | **必須** | `ブロッコリー` (label と同じ場合は省略可) | 表記揺れの起点 |
| **同名のひらがな表記** | **必須** | `ぶろっこりー` | カタカナ→ひらがな変換が無くてもヒット |
| **同名のローマ字表記 (ヘボン式)** | **必須** | `burokkori`, `burokkoorii` | 日本語入力前提でも素早い検索を可能に |
| **英語名** | **推奨** (主要食材のみ) | `broccoli` | §11 #1 の解決方針: あすけん頻出 × 一般定着 100食材に限定 |
| **省略形/口語/別名** | **推奨** | `ブロッコリ` (長音省略) など | ベンチで頻出する表現を拾う |

#### 5.4.3 0件クエリの運用フィードバックループ

#### 5.4.4 メンテルール

- Identity 追加時に **最低3つ** の `searchTags` を必須化 (label カナ + ひらがな + ローマ字)
- 例外: label が既にひらがな or 漢字 (例: `ごはん` `卵`) の場合でも、カナ + ひらがな別表記 + ローマ字を必須とする
- 担保方法: PR テンプレ項目に「searchTags ≥ 3 件 (ひらがな + ローマ字を含む)」を追加。中長期では ESLint カスタムルールも検討
- 既存 Identity (115件中 103件が searchTags 未定義 — §6.1 脚注参照) は Phase 2 投入前のデータ整備フェーズで一括補充する


- **バケット単位で十分**。Identity まで特定しようとしない (PFC 収束の前提により、バケットが当たれば実用上足りる)
- 初版は §1.4 の実測で「手がかりゼロ」だった23件 + あすけん頻出語から **200〜300語**を目安に着手
- 既存の `CATEGORY_KEYWORD_MAP` (`identity-search.ts`、現在18バケット分のみで明らかに手薄) を**この辞書に統合・置換する**

#### 5.4.7 辞書育成ループ (§5.4.3 の拡張)

1. `recordSearchMissEvent` が **層1でヒットしなかったクエリ**を記録する (F5 の発火条件を参照)
2. 月次で 0件クエリを頻度順に抽出
3. 振り分け:
   - 既存 Identity/Attribute の表記ゆれ → `searchTags` に追記
   - 複合語で主辞が既知 → 主辞辞書 (§5.4.5) に追記
   - 未知の単一語 → 料理名辞書 (§5.4.6) に追記
   - **どのバケットにも収まらない栄養プロファイル → ここで初めて Identity 追加 (P2-S3) を検討**
4. 3の上3つは設計レビュー不要で機械的に追加できる。**Identity 追加は最後の手段**

### 5.5 ローマ字→ひらがな辞書範囲

#### 5.5.1 採用方針

**ヘボン式優先 + 訓令式の主要パターンを併存** (両方の入力で同じひらがなに変換する)

理由:
- ヘボン式は実用 (パスポート / 道路標識 / 駅名表示) で広く使われる
- 訓令式は学校教育・公的記録で使われる
- 両方カバーすることで「`shi` でも `si` でも『し』にヒット」を保証する

#### 5.5.2 主要マッピング例

| ローマ字入力 | ヘボン式 | 訓令式 | 採用 |
|---|---|---|---|
| `shi` / `si` | し | し | 両方 → し |
| `chi` / `ti` | ち | ち | 両方 → ち |
| `tsu` / `tu` | つ | つ | 両方 → つ |
| `fu` / `hu` | ふ | ふ | 両方 → ふ |
| `ja` / `zya` | じゃ | じゃ | 両方 → じゃ |
| `kya` | きゃ | きゃ | (同じ) |
| `kk` (促音) | っk | っk | 子音重複から `っ` 生成 |
| `ou` / `oo` (長音) | おう / おお | おう / おお | 両方を保持 (元表記 + 長音除去版) |

#### 5.5.3 辞書サイズと実装

**約 200 エントリ** で網羅可能:
- 清音: 46
- 濁音/半濁音: 25
- 拗音 (kya, sha, cha, ...): 35
- 撥音 (n, nn): 2
- 促音 (kk, tt, ss, ...): 子音重複処理ロジック
- 訓令式エイリアス: ヘボン式と異なるパターンのみ (約 15)
- 長音処理 (ー, ou, oo, uu, ei): 専用ロジック

**辞書ソースの判断:**
- 採用方針: **内製辞書** (200件なら依存追加不要、bundle size への影響ゼロ)
- 既存ライブラリ `wanakana` (npm, ~30KB) は実装ゼロだが依存増 → 当面は内製、複雑化したら再検討

#### 5.5.4 トークナイズ戦略

**最長一致** で先頭から消費する:
1. 入力: `"sashimi"`
2. 先頭から最長 3文字 → 2文字 → 1文字の順でマッチ試行
3. `"sa"` → `さ` (2文字消費), `"shi"` → `し` (3文字消費), `"mi"` → `み` (2文字消費)
4. 結果: `"さしみ"`

トークナイズに失敗した残文字 (例: `"xyz"`) はそのまま結果に残す (検索クエリ側ではゼロマッチを許容する保険として機能)。

- **スコープ**: 全 Identity (kanji含む69件) に最低1件のひらがな読みを付与。ローマ字は §F2-1 (`romajiVariant`) が既に汎用対応しているため個別付与は不要と判断し、当初案の「ひらがな+ローマ字+別表記=最低3件」から縮小した
- **Attribute/Style層への拡張**: 実装過程で「ユーザーが探す名前は Attribute 層に集中している」(§1.4) ことが判明したため、`AttributeOption.searchTags` / `StyleOption.searchTags` を型に新規追加 (`types/identity.ts`) し、`identity-search.ts` の `targetsFor()` に配線した。**当初 Phase 1.5 の対象外だった層まで踏み込んでいる**

- **未対応 (残タスク)**: `だし巻き卵` `おでん` `もつ煮` `ハムカツ` `ラテ` 等、DB に**Identity/Attributeとして存在しない**語は今回のデータ整備では解決しない (§5.4.6 料理名辞書=P3、または新規Identity/Attribute追加の対象)

- **`からあげ`(ひらがな)→`唐揚げ`(漢字) は P2 の範囲外と判明した。** 正規化は文字種変換(かな⇄かな、ローマ字→かな)であり、kanji→reading の変換は含まない。これは §5.4.4 の**データ整備**(searchTags にひらがな読みを追加する) で解決するものであり、Phase 1.5 の対象。当初 Phase 2 の効果例として挙げていた「からあげ / ゆで卵 / avocado」は不正確だったため上表から削除した
- **ローマ字変換は target 側 (Identity/searchTags) には適用しない、query 側のみの追加候補として扱う。** target 側まで変換すると英語 searchTags の前方一致 (`chick`→`chicken`) が壊れる (貪欲最長一致トークナイズは文字列の切れ目で分岐するため prefix 関係が保存されない)。詳細は `identity-normalize.ts` 冒頭コメント
- 受け入れテスト: `expo/utils/identity-normalize.test.ts` に T2/T3/T4/T10 相当 + 訓令式/ヘボン式等価性 + 英語prefix非破壊を追加 (13件、全通過)
- 実機確認: `burokkori` (ローマ字) / `ﾌﾞﾛｯｺﾘｰ` (半角カナ) が「ブロッコリー」にconfidentヒットすることをWeb previewで確認

#### P3 実装ノート (2026-08-10)

- 実装位置: `expo/constants/identity/head-nouns.ts` (主辞辞書、新規) / `expo/constants/identity/dish-vocabulary.ts` (料理名辞書、新規)。§5.4.6 の指示通り、旧 `CATEGORY_KEYWORD_MAP` (層4のカテゴリヒント用、18バケット分の手薄なキーワードリスト) は `DISH_VOCABULARY` に統合・置換した — 層3(確定的な単語辞書)と層4(緩いキーワードスキャン)が同じデータソースを異なる粒度で参照する構成
- **層2/3 の優先順位**: 料理名辞書 (層3、単一語への確定的な着地) を主辞辞書 (層2、末尾一致による推測) より先に照合する。「たい焼き」のように辞書に直接登録されている語のほうが、末尾主辞「焼き」だけからの推測 (たい焼き=菓子 / 生姜焼き=肉、§5.2.2) より具体的で信頼できるため
- **主辞辞書の表記**: `heads` にひらがな形だけでなく漢字形も併記する (`['やき', '焼き', '焼']` 等)。`normalize()` は文字種変換のみで漢字→読み変換を行わないため、「筑前煮」「だし巻き卵」のようにクエリが漢字のまま入力されるケースは漢字形の主辞でしか拾えない (Phase 1.5 実装ノートで判明した限界の直接対応)
- **実装中に見つけた既存バグ2点を合わせて修正**:
  1. 主辞辞書の一部エントリ (`しちゅー`,`けーき`等) に長音符 `ー` を含めたまま登録していたため、`normalize()` が長音符を除去したクエリと一致しなかった。`HEAD_NOUNS_INDEX` で正規化してから比較する方式に変更し、以後この種の表記ゆれで再発しない設計にした
  2. `scoreAgainst()` の部分一致 (substring) に最小文字数の制約が無く、`フォー`→正規化後2文字「ふぉ」が無関係な「クアトロ・フォルマッジ」に部分一致して confident 判定されていた (実装中の検証で発見)。q.length ≥ 3 を部分一致の条件に追加。副作用として `餃子`→`水餃子` が confident から maybe (bigram) に降格したが、52件中1件のみで実害は限定的と判断
- **層4との重複排除**: 層2/3 (もしかして) で既に出たバケットは、層4 (このカテゴリかも) では同じチップを重ねて出さないようフィルタする (`SearchSheet.tsx`)。両者が同じ `DISH_VOCABULARY` を参照する設計上、素朴に両方表示すると同一チップが二重に出ていた
- **収録範囲**: 主辞辞書 約45エントリ (調理法/料理形式/主食/惣菜/菓子/食材)、料理名辞書 222語 (2026-08-11時点。§1.4 実測の「手がかりゼロ23件」全件 + 旧 CATEGORY_KEYWORD_MAP 吸収分 + 洋食/中東・地中海/東南アジア・南アジア/韓国/中華/朝食・パン/飲み物/肉料理/野菜サラダ/和菓子/主食粉もの/寿司/サンドバーガー、デスクリサーチベースで拡充)。§5.4.6 が目安とする200〜300語のレンジに到達した。拡充時、主辞辞書 (head-nouns.ts) の語尾 (焼き/揚げ/丼/汁/鍋/カツ/煮/和え/漬け等) で既に拾える語は二重登録しない方針を徹底した。無糖茶・水はPRD方針上ログ対象外のため意図的に未収録。残りの伸長は §5.4.7 の辞書育成ループ (0件クエリの月次運用) で実データから継続する
- 受け入れ確認: §1.4 の「手がかりゼロ23件」ベンチマークで全件が層2/3いずれかで着地することを確認 (グラタン/ドリア/ポトフ/ミネストローネ/天津飯/フォー/パッタイ/ケバブ/パエリア/リゾット/ラザニア/ドーナツ/たい焼き/おしるこ/チヂミ/ナムル/ビリヤニ/おでん/ハムカツ/ビーフシチュー/ハヤシライス/ひじき煮/筑前煮/もつ煮/だし巻き卵)。既存の層1 confident ヒット19件 (からあげ/親子丼/麻婆豆腐等) に回帰なし。Web previewで `グラタン`(層3単独ヒット)・`たい焼き`(層2の2候補) を確認

#### P4 実装ノート (2026-08-10)

- 実装位置: `expo/utils/identity-search.ts` の `searchEntriesFuzzy(query, opts?: { history })`。第2引数で `settings.quickLogHistory` (⭐️タブ/自動学習と同じデータソース) を受け取り、層内の並び順にのみ反映する
- **user 項の実装**: `QuickLogSelection.subcategoryKey` は Identity-first IA 由来のエントリでは常に record Identity の id と一致する (`identity-log-bridge.ts` の `subTypeKey: recordIdentity.id`)。これを利用し `(identity.id, attrKey, styleKey)` 単位で選択回数を集計し、`finalScore = matchScore × (1 + 0.5 × log(1+count))` で並び替える。新規の頻度データストアは作らず、既存の学習基盤にそのまま乗せた
- **global 項は実装しない** (§5.3 参照)。捏造データを入れるくらいなら明示的に省略する判断
- **層の判定には影響させない設計**: `results.filter(tier === 'confident')` 等のフィルタは元のマッチスコア/手法で確定した `tier` を見るのみで、頻度で層をまたぐ格上げは起きない。頻度の影響は各層内の `sort()` のみに限定
- 受け入れ確認: `唐揚げ` 検索で、通常は末尾に来る「唐揚げ弁当」を10回選択した履歴を与えたところ、確信度層(confident)内で先頭に繰り上がることを単体テストスクリプトと Web preview の両方で確認。履歴が無い場合は従来通りマッチスコア順のまま (回帰なし)
