## 1. 目的

本プロダクトの目的は、ユーザーがアプリ開始直後に「自分の今の体型」と「なりたい体型」を直感的かつ納得感を持って把握し、その内容をもとに、無理のない体重・体脂肪率・摂取カロリー・PFCバランスの初期提案を受けられる状態を作ることです。加えて、初回から食事記録をしやすくするために、オンボーディングで取得した嗜好や食行動の傾向をクイックログUIへ反映し、初期体験の摩擦を下げます。

体型分類は「体脂肪だけ」で見せるのではなく、**脂肪量 × 筋量の二軸** で整理した共通9分類を採用します。これにより、「細いけれど筋肉が少ない」「重いけれど筋肉が多い」など、現実の見た目に近い分類を表現でき、現在体型と目標体型を同じ概念体系で扱えます。分類思想の根拠は、Tanitaの体組成タイプ判定、InBodyの筋肉量・脂肪量の複合評価、日本のBMI/体脂肪率目安に基づいています。

## 2. 対象ユーザー

### 2.1 コアターゲット
ダイエット・ボディメイク・健康管理に関心はあるが、専門的な身体指標には詳しくない一般ユーザー。特に、「痩せたい」だけではなく「引き締めたい」「筋肉をつけたい」「健康的に整えたい」といった、見た目ベースで目標を考える人。

### 2.2 主要ユーザー像
- **A: なんとなく体型を整えたい初心者** — 数値より見た目で判断したい。BMIや体脂肪率だけでは目標が分かりにくい。
- **B: 食事管理を始めたいが入力が面倒な人** — 最初の入力負荷が高いと離脱しやすい。
- **C: 体重だけでなく体型の変化を重視する人** — 同じ体重でも見た目が違うことを理解している。

## 3. プロダクト方針

### 3.1 体型定義の基本方針
現在体型と目標体型は、**同じ9分類マトリクス** で扱う。「現在は9分類、目標は5分類」などの不一致は採用しない。

### 3.2 9分類マトリクス（脂肪 × 筋量）

体型分類は **脂肪3段階 × 筋量3段階** の9セルで定義する。
**命名 (「スリム」「バランス」等) は一切付与しない** — 価値判断や羞恥を生まないために、表記は **軸ラベルの組み合わせのみ** とする。

両軸のラベルは **「少なめ / ふつう / 多め」** で統一する (認知負荷最小化)。

|              | 脂肪 **少なめ**   | 脂肪 **ふつう**   | 脂肪 **多め**     |
|--------------|-------------------|-------------------|-------------------|
| **筋量 少なめ** | fat↓ / musc↓    | fat→ / musc↓     | fat↑ / musc↓     |
| **筋量 ふつう** | fat↓ / musc→    | fat→ / musc→     | fat↑ / musc→     |
| **筋量 多め**   | fat↓ / musc↑    | fat→ / musc↑     | fat↑ / musc↑     |

UI/My Statusでの表記例: 「**脂肪 · ふつう × 筋量 · ふつう**」

#### 9タイルの参考値テーブル

各セルに紐づくBMI中央値とBF%中央値を定義する。オンボーディングUIでは、ユーザーの身長に応じた **参考体重 (= BMI × 身長²)** と **BF%の目安** を動的に表示する。

**男性基準**
|              | 脂肪 少なめ    | 脂肪 ふつう    | 脂肪 多め      |
|--------------|---------------|---------------|---------------|
| 筋量 少なめ   | BMI 18 / BF 12% | BMI 20 / BF 20% | BMI 25 / BF 27% |
| 筋量 ふつう   | BMI 20 / BF 12% | BMI 23 / BF 17% | BMI 26 / BF 25% |
| 筋量 多め     | BMI 22 / BF 10% | BMI 25 / BF 15% | BMI 28 / BF 22% |

**女性基準**
|              | 脂肪 少なめ    | 脂肪 ふつう    | 脂肪 多め      |
|--------------|---------------|---------------|---------------|
| 筋量 少なめ   | BMI 17 / BF 20% | BMI 20 / BF 26% | BMI 24 / BF 33% |
| 筋量 ふつう   | BMI 19 / BF 20% | BMI 22 / BF 25% | BMI 25 / BF 31% |
| 筋量 多め     | BMI 21 / BF 18% | BMI 24 / BF 23% | BMI 27 / BF 29% |

### 3.3 見た目表現の方針
- リアル写真ではなく、中立的な **フラットベクターSVGイラスト**
- 比較可能性 / UI統一性 / 非性的・非評価的 / スケーラビリティ重視
- 基準マスター: **男性M5・女性F5** をシリーズ中心点として固定

### 6.2 基礎データ取得 & 現在体型の選択

#### 6.2.2 現在体型の選択UI (自動推定ではなくユーザー選択)

従来の「4項目から自動推定」方式ではなく、**ユーザーが見た目で9分類から選ぶ** 方式を採用する。理由:
- 体脂肪率を知らないユーザーの離脱を防ぐ
- PRD想定ユーザーA (「数値より見た目で判断」) にフィット
- 9分類マトリクスを中核UX (PRD §3.2) として主役化できる

**UI仕様**:
- 9タイルを3×3のマトリクス表示 (イラスト+軸ラベル+参考値)
- 各タイルに、ユーザー入力値から動的算出した **参考体重 (身長から)** と **BF%目安** を表示
  - 参考体重 = `セルのBMI × (身長/100)²`
  - BF% = §3.2 テーブル値
- ユーザーの現在BMIから**近似タイルを控えめにハイライト** (選択は自由)
  - 距離 = `|userBMI - tileBMI| / 3`
- タイル選択後、**BF%が自動入力される** (タイル中央値)
- BF%は下部のフィールドで編集可: "体脂肪率 17% (目安) ▸" → タップで入力モードに
- ユーザーが手入力すると "(目安)" → "(入力済)" 表示に変化
- **派手な結果演出はしない** (静的表示のみ)

#### 6.2.3 運動習慣の取得 (1問)
PRD §6.4 のマクロ目標算出に活用する。体型選択そのものには使わない。

| Lv | 選択肢 | 想定する人 | 活動係数 | タンパク質目安 (維持時) |
|----|--------|-----------|---------|---------------------|
| 1 | ほとんど運動しない | デスクワーク中心・座りがち | 1.20 | 1.2 g/kg |
| 2 | 軽めに動く | 週1–2回の散歩・軽い運動、立ち仕事 | 1.38 | 1.4 g/kg |
| 3 | よく運動する | 週3–4回の運動 or 筋トレあり | 1.55 | 1.6 g/kg |
| 4 | しっかり鍛えている | 週5回以上・筋トレ中心・スポーツ | 1.73 | 1.8 g/kg |

- 体型未選択時は Phase 3 に進めない

### 6.3 目標体型の決定 (目的 + プラン)

**v1.3 変更**: 目標体型を 9-マトリクスから手動選択する UI は廃止し、**目的 (減量/維持/増量) 1問** + **ペース選択 (3択)** から自動導出する方式に統一した。ユーザーの認知負荷を下げ、目的 ↔ 目標セルの整合性を構造的に保証する。

**UI仕様** (オンボ / goal-edit 共通):
- **目的 (direction)** を 3択で選択: `減らす / 維持 / 増やす`
- 選択された目的から目標セルを `deriveTargetCellFromDirection(current, direction)` で自動導出
  - 減量: 脂肪軸を 1段階下げる (既に最小なら現セル維持)
  - 維持: 現セル
  - 増量: 筋量軸を 1段階上げる (既に最大なら脂肪軸を 1段階上げる = リーンバルク)
- 目標体重/BF% は §6.4 の `computePlanOutcome` により **ユーザーの現在値 × ペース** から計算される
  - **(v1.7)** ただしこの試算値は**コミット時に一度だけ固定アンカーとして確定**し、以後の体重変化や目的/ペースを変えない再保存では動かさない (ドリフト防止規則 → §6.4.4)
- オンボでは「**3ヶ月後、どう変わりたい？**」として 3プランカード (ゆるやか/標準/しっかり) を並列比較表示する
  - 各カードに 3ヶ月累計 kg差 / 月次目安 / BF%変化 / 目標体型シルエット / "体型が変わるペース" or "変化は小さめ" ヒント
  - 標準プランには **「おすすめ」バッジ**

**ポジティブな演出について**:
目標確定時は、ユーザーのコミットを後押しするために**ポジティブな演出を許容** する (例: アクセントカラーのアニメーション等)。具体的な演出設計は別論点として別途検討 (TBD)。

**受け入れ条件**:
- 目的を選ぶだけで、目標セル・目標体重・目標BF%・kcal/PFC が一意に決まる
- プランを切り替えると上記が即座に再計算される
- 目的「維持」選択時はペース選択をスキップ (ペース無関係)
- **(v1.7)** 目的・ペースを変えずに goal-edit を再保存しても目標体重は変化しない (固定アンカー, §6.4.4)

### 6.4 目標数値提案

#### 6.4.1 算出ロジック

**RMR (基礎代謝)**
- 体脂肪率 **未入力** の場合: Mifflin-St Jeor 式
  - 男性基準: `9.99×体重 + 6.25×身長 - 4.92×年齢 + 5`
  - 女性基準: `9.99×体重 + 6.25×身長 - 4.92×年齢 - 161`
- 体脂肪率 **入力あり** の場合: Katch-McArdle 式 (精度優先)
  - `370 + 21.6 × LBM` (LBM = 体重 × (1 - 体脂肪率/100))

**TDEE (消費カロリー)**
- `TDEE = RMR × 運動習慣の活動係数` (§6.2 Lv1〜4)

**目標カロリー**
- 基本: **体重%ベース** で deficit / surplus を決める
  - 減量: `TDEE - (体重 × 7.7 × 減量ペース係数)` ≒ 体重の **0.5–1.0%/週減** に相当
  - 維持: `TDEE`
  - 増量: `TDEE + (体重 × 3.85 × 増量ペース係数)` ≒ 体重の **0.25–0.5%/週増** に相当
- 最低保証: 男性1500kcal / 女性1200kcal を下限としてクリップ
- ペース選択「ゆるやか / 標準 / しっかり」で係数を 0.5x / 1.0x / 1.5x 調整

**タンパク質 (g)**
- 体重kgベース:
  - 維持: 運動習慣のP目安 (1.2〜1.8 g/kg)
  - 減量: 維持値 + **0.3 g/kg** (筋肉温存)
  - 増量: 維持値 + **0.2 g/kg**
- 計算結果の kcal% は 13–35% の範囲で自動クリップ

**脂肪 (g)**
- 下限ガード: **体重 × 0.6 g/kg** または 総kcal × 20% のうち大きい方
- 減量中の上限: 総kcal × 30%

**炭水化物 (g)**
- 残りカロリーから算出: `(目標kcal - P×4 - F×9) ÷ 4`

**目標体重 / 目標BF% (v1.3)**
- 優先順位1: **プラン試算** (`computePlanOutcome`) — 現在体重/BF% × ペース係数で 3ヶ月後を予測
  - 減量: 週次 -0.25% / -0.5% / -0.75% × 13週 → 体重差 → 最終体重
  - BF%: 減量時は 75% が脂肪量減と仮定して再計算
  - 増量: 週次 +0.125% / +0.25% / +0.375%、30% を脂肪増と仮定
- 優先順位2: **セル参考値** (`getCellRef` の BMI 中央値 × 身長²) — ペース未選択時のフォールバック
- **維持時 (v1.7 改訂)**: §6.4.4 の切替ルールに従う。減量ゴール未到達なら「減量継続 / 現体重で維持」を確認。到達済み・初回維持なら現在体重をアンカー
- **(v1.7) 上記試算は「予測」。コミットで確定した値は固定アンカーとして凍結**し、体重変化・単純な再保存では動かさない → §6.4.4

- 「目標まであと ○kg」の残量テキストは現在値とアンカーの差分で表示してよい (バー無しでも可)。

**警告**
- 極端設定時 (1200kcal 切れ / 減量ペース週 1.0% 超等) は注意文を表示

#### 6.4.3 動的TDEE — 活動量による日次目標補正 (差分方式, v1.8)

> Health Connect / Apple Health から取得した当日の活動量を、日次のkcal目標へ **差分方式** で反映する。
> 設計の前提は ROADMAP B レーン参照。**全額加算はしない** — 二重計上を避けるため、係数が想定する基準活動量を超えた分のみ上乗せする。

**前提: 活動係数に既に含まれる活動量**
- `TDEE = RMR × 活動係数 (§6.2 Lv1〜4)`。この活動係数は「日常移動を含む1日全体」を表す標準PAL値。
- したがって**活動係数が想定する1日のアクティブエネルギー (基準活動量) は次で求まる**:
  - `baselineActiveKcal = RMR × (活動係数 − 1)`
  - 例: RMR 1,500 / Lv1 (1.2) → 基準 300 kcal、Lv3 (1.55) → 基準 825 kcal
- この基準分は **既に targetCalories に織り込まれている**。歩数/activeKcal を全額足すと二重計上になる。

**差分の算出 (基準超過分のみ加算)**
- 当日の実測アクティブエネルギーを `measuredActiveKcal` とする (Health の Active Energy。歩数しか取れない場合は `歩数 × 体重kg × 0.0005 kcal/歩` で近似)。
- `activityExcess = max(0, measuredActiveKcal − baselineActiveKcal)`
- 普段の日: measured ≈ baseline → excess ≈ 0 → 加算なし → 目標が安定。
- 登山・旅行等: measured が基準を大きく超える → excess を加算。

**運動ログとの二重計上調停 (必須)**
- `measuredActiveKcal` には手動記録した運動 (ExerciseLog) の消費も含まれる。両方を足すと運動分が二重計上される。
- 調停ルール: **「活動由来の加算」と「運動ログ由来の加算」の大きい方を採る**。
  - `exerciseAddition = Σ ExerciseLog.netKcal (当日)` (現行 `adjustedTargetKcal` の挙動)
  - `activityAddition = min(activityExcess, DAILY_CAP)`
  - `finalAddition = max(exerciseAddition, activityAddition)`
- 根拠: activeKcal は運動も日常も包含するため、Health が完全に取れていれば activityAddition ≥ exerciseAddition となり運動分を含む。Health 未連携・未取得なら activityAddition = 0 で **現行挙動 (運動ログのみ) に自動フォールバック** = 後方互換。

**日次キャップ (異常値吸収)**
- `DAILY_CAP` = 800 kcal (GPSノイズによる5万歩等の異常値を吸収。実用上は登山20,000歩でも基準超過 ~600-800kcal に収まる想定)。

**最終目標**
- `adjustedTargetKcal = targetCalories + finalAddition`
- リング分母・「残り kcal」表示に反映。UX 文言は「今日 +○○ kcal の余裕」(目標の置き換えではなく上乗せとして見せる)。

**歩数の別用途 (係数見直しサジェスト)**
- 日次加算とは独立に、直近の平均 `measuredActiveKcal` が選択中の活動レベルの基準から継続的に乖離している場合、活動係数の見直しを中立トーンで提案する (PRD §9.1 準拠)。これにより歩数誤差を「日次の不安定な加算」ではなく「恒常的な係数精度の向上」に効かせる。

**境界 (In Scope / Out)**
- In: 当日活動の差分加算、運動ログ調停、日次キャップ、係数見直しサジェスト。
- Out (§4.2 維持): 心拍ベースの精密TDEE、医療的な代謝判定。

#### 6.4.5 今週の収支を合わせる (旧「帳尻調整」, v1.13)

> 日々の目標どおりに食べる日ばかりではない。多かった日・少なかった日の差を、**同じ週の残りの日でならす**ためのオプション。
> 旧仕様 (前日のオーバー分だけを N 日に割って差し引く) は少なかった日を見ておらず、「1週間で合わせる」になっていなかったため置き換えた。

**オプションであること (最重要)**
- **自分で始めたときだけ効く。** 常時オンにはしない。細かくやりたくない人にとって、目標が勝手に変わるのは違和感になるため
- 始める入口は2つ: ホームの提案バナー / 収支モーダル (リング中央タップ) の行
- **その週だけ有効**。日曜が終わると自動で通常の目標に戻る。翌週は差が出たときにまた提案するだけ (勝手に引き継がない)
- 途中でやめられる (やめると今日から通常の目標)

**週の区切り**: 月曜始まりの固定週 (週次振り返り §6.7.5 と同じ `getWeekRange`)。
- 直近7日の移動窓は「いつ合うのか」が見えにくいため不採用
- 代償として、日曜の差は翌週へ持ち越さない (月曜は常に差 0 で、提案も出ない)

**計算**
- その日の目標 `target(d)` = §6.4.3 の `adjustedTargetKcal` (ベース目標 + 活動・運動の加算)
- 週の差 `balance = Σ (consumed(d) − target(d))` — 月曜〜**昨日**のうち**記録のある日**だけ。+ が多め、− が少なめ
  - **今日は含めない** (食べるたびに今日の目標が動くと、何を目安にすればいいか分からなくなる)
  - **記録のない日 (その日の kcal が 0) は計算から外す。** 外さないと、つけ忘れた日が丸ごと「少なめ」として数えられ、実態のない「ゆとり」になる (週次振り返りの「未記録 = 欠測」と同じ扱い)
- 今日への加減 `adjustment = round(−balance ÷ 残り日数)`。残り日数 = 今日から日曜まで (今日を含む)
- 今日の目標 = `target(今日) + adjustment`
- 毎日計算し直すので、調整中に多め/少なめの日があっても次の日の値に自然に反映される (旧仕様の「固定額を差し引き続ける」は廃止)
  - 差は**調整後ではなくその日の元の目標**と比べる (週の予算は元の目標の合計で、調整は配り方にすぎない)。調整後の目標どおりなら翌日も同じ額、下回ればゆるみ、週の差がマイナスに転じればゆとりに変わる
  - 調整中に記録しなかった日は差に数えず残り日数だけ減るため、調整がその後の日に寄る。「調整後の目標どおりに食べた扱い」にする案は「記録のない日は数えない」原則と食い違うため不採用 (2026-10-10)

**ガード (方向で非対称)**
- **控えめ側**: 今日の目標が `1,000 kcal` (絶対床, `CARRYOVER_HARD_FLOOR_KCAL`) を下回らないよう調整額を止める。止めた分は残りの日に回り、日曜で吸収しきれなければ捨てる (週をまたいで借りを積み上げない)。注意の閾値 (男性基準 1,500 / 女性基準・不明 1,200 kcal) を下回るときは事実として知らせるが止めない
- **ゆとり側**: 1日あたり **ベース目標の +15%** まで。記録しきれていない日 (軽食のつけ忘れ等) があると、実際以上に「少なめ」に見えるため、上方向は控えめ側より強く抑える

**提案の出し方**
- 調整していない週で、`|balance|` がベース目標の 15% を超え、午前中で、今日まだ閉じていないとき、ホームにバナーを出す (多め/少なめの両方向)
- 調整中は、今日の加減を伝えるバナーを出す (その日に閉じれば消える)
- 文言は評価しない (VOICE.md): 「今週の食事、ここまで少し多めです」「少なめです」。「取り戻す」「挽回」「ご褒美」は使わない

**表示**
- リング・残り kcal・PFC の目安・ウィジェットは、調整込みの今日の目標を使う
- 収支モーダルに「今週の調整」行 (± kcal) を出す
- 過去日の表示は調整を含まない (調整は今日に対してだけ計算する)

**受け入れ条件**
- 月〜水に +600 kcal 多めの週、木曜に始めると、木曜の目標は `−150 kcal` (残り4日)
- 記録のない日は差に入らない (火曜を記録しなかった週で、火曜の目標分が「少なめ」に数えられない)
- 少なめの週でも、ゆとりは1日ベース目標の15%を超えない
- 今日の目標が 1,000 kcal を下回らない
- 翌週の月曜には自動で通常の目標に戻る

#### 6.4.4 目標アンカーとドリフト防止 (v1.7)

> **背景**: v1.3〜v1.6 では `targetWeightKg` / `targetBodyFatPct` を「現在体重 × ペースの 3ヶ月試算 (`computePlanOutcome`)」で**都度算出し、目標を再保存するたびに現在体重を起点に引き直していた**。このため減量中に目標を編集・再保存すると最終ゴールが手前にずれ (例: 80→73kg を目指していたのが、77kg 時点の再保存で約 74kg へ後退)、特に「減量→維持」切替時は維持目標が**現在体重に無言で固定**され、ユーザーが当初描いたゴールが失われていた。競合 (MacroFactor / MyFitnessPal / あすけん) はいずれも**目標体重をユーザー確定の固定アンカー**として保持し、現在体重から引き直さない。本節でこの方針に統一する。

**概念の分離 (予測 ≠ 目標)**
- **予測 (forecast)**: 「このペースなら 3ヶ月で約○kg」のライブ試算 (`computePlanOutcome`)。現在体重に追従して**動いてよい**。あくまで情報提示。
- **目標 (committed goal / anchor)**: ユーザーがコミットした最終ゴール。**確定時に一度だけ固定し、以後の体重変化や目標の単純な再保存では動かさない**。
- 現状この 2 概念を `targetWeightKg` 単一フィールドが兼務しているのがドリフトの根因。アンカーとして再定義する。

**スナップショットは持たない (簡素化, v1.7)**
- 当初検討した `initialWeightKg` / `initialBodyFatPct` (旅の出発点) は**導入しない**。進捗を「出発点 → 現在 → 目標」の 3 点バーで見せる方針を撤回し、**体重/BF% の推移チャート + 目標ライン**に一本化したため (§6.4.2 / §6.6 進捗表示)。出発点はチャート上の過去データとして自然に写る。
- ドリフト是正の本体は **`targetWeightKg` / `targetBodyFatPct` を凍結アンカー化する一点**に集約する。新フィールド追加は原則不要。
- `goalStartedAt: string` (目標設定日) のみ、必要なら任意で保持してよい (UI 必須ではない)。

**確定 (commit) と更新規則**
- `targetWeightKg` / `targetBodyFatPct` を更新するのは、**ユーザーが目的 (direction) もしくはペース (pace) を実際に変更して保存した時のみ** (= 明示的な再コミット)。
- 目的・ペースを変えずに goal-edit を保存しても、**目標アンカーは据え置く** (ドリフト禁止 / no-op)。変更がなければ保存ボタンを非活性にしてよい。
- 体重・体脂肪の記録 (`addWeightEntry` / `BodyFatEntry`) は `currentWeightKg` / `currentBodyFatPct` のみ更新し、**目標体重には一切触れない** (現行どおり)。
- `targetCalories` / PFC は最新の代謝に追従させる意義があるため現在体重ベースの再計算を許容するが、**目標"体重"アンカーとは別管理**として混同しない。

**減量・増量の目標体重**
- コミット時に `computePlanOutcome(現在体重, ペース)` で最終体重を一度算出し、**アンカーとして凍結**。
- goal-edit 再表示時は凍結済みアンカーを表示。ペース変更時のみ再算出 (= 新アンカーで再コミット)。

**目標体重の手動指定 (任意 / 逃げ道, v1.7)**
- 既定フローは **目的＋ペースからの自動導出**のまま (初心者の認知負荷・ウェルネストーン・9マトリクス整合を守る)。手入力は**主役にしない**。
- 具体的な数値目標を持つユーザー向けに、目標体重を直接指定できる。入力した値が `targetWeightKg` アンカーになる。

  **動線 (確定仕様)**:
  1. **入り口** = プレビューカードの**目標体重ヒーロー数値に編集アフォーダンス (✎)**。タップ編集に入った瞬間が手入力モードへの切替 (「モード」という語はUIに出さない)。数字キーパッド入力 + ±0.5kg ステッパー。
  2. 手入力モードでは **目的セグメントを隠し**、入力体重 vs 現在体重から目的 (減/維/増) を**自動導出**する (矛盾の余地を消す)。
  3. **ペースは残す** (速度＝kcal)。手入力した行き先に対し「標準ペースで約○ヶ月の目安」と結果 (ETA) を情報提示する。期限主導モード (date→pace 逆算) ではない。
  4. カード上に「自分で設定 ｜ **おまかせに戻す**」を表示。戻すと手入力を破棄し目的セグメント再表示・target 再計算で既定へ復帰。
  5. **維持の特例**: 入力値＝現在体重で自動導出が「維持」になる場合はペースも隠す。数値自体が明示的な意思表示のため、§6.4.4 維持切替の「減量継続/現体重維持」確認ダイアログはスキップする。
- **設計境界 (安全)**: 手入力が変えるのは**行き先 (アンカー) のみ**。`targetCalories` / PFC は従来どおり「現在体重 × ペース」から算出し、**目標体重では変えない** → 目標を低く入れても危険な低カロリーにならない (目標＝行き先, ペース＝速度を分離)。
- **ガードレール (エビデンスベース)**: 目標体重の BMI で3段階に判定する。「現在の状態」ではなく「目指す目標」を弾く設計 (摂食障害域を正当化しないため)。
  | 区分 | BMI 範囲 | 挙動 | 根拠 |
  |---|---|---|---|
  | 普通体重 | **18.5〜25** | 通常 | 日本肥満学会 (普通体重)・WHO |
  | ソフト警告 | **<18.5** または **>25** | 事実のみ表示・**保存可** (amber) | WHO 低体重 / JASSO 肥満境界 (日本主対象のため上限は欧米の27/30でなく25) |
  | ハード制限 | **<17.5** | **保存不可** | 摂食障害の臨床紹介基準 (MARSIPAN / RCPsych)。目標を臨床紹介域に置かせない |
  - 上限のハード制限は健康上**設けない** (高い目標体重は飢餓を促さない)。入力欄の既存レンジ (30〜200kg) でサニティのみ担保。
  - **二次防御**: 既存のカロリー下限 (男1500 / 女1200, §6.4.1) を維持し、目標体重が低めでも摂取kcalが危険値にならないよう二重化する。
  - heightCm 未設定時は BMI 算出不可のため判定をスキップ (警告・ブロックなし)。
  - 体型セル / 目標BF% は手入力体重と矛盾しないよう整合させる (セルは見た目補助、アンカーは数値優先)。
  - 出典: WHO BMI 分類 (severe thinness <16 / 紹介・緊急域)、日本肥満学会 肥満度分類 (普通体重 18.5〜25)、MARSIPAN (紹介 <17.5)。

  **文言 (確定 / 中立・非評価トーン)**:
  | 要素 | 文言 |
  |---|---|
  | 既定タグ / 手入力タグ | `おまかせ` / `自分で設定` |
  | 復帰リンク | `おまかせに戻す` |
  | 差分 (減 / 増 / 同値) | `現在 77.0 → 目標 73.0（−4.0 kg）` / `…（＋3.0 kg）` / `現在の体重を維持します` |
  | ETA (ペース名入り) | `標準ペースで約 2.5 ヶ月の見込み` (`ゆるやか`/`しっかり` も同型・ヶ月は0.5刻み丸め・1ヶ月未満=`約 3 週間`・12ヶ月超=`1 年以上`・維持時は非表示) |
  | 健康レンジ警告 (低 <18.5 / 高 >25) | `標準的な体重の目安より低めです（BMI 17.9）` / `標準的な体重の目安より高めです（BMI 26.4）` (事実のみ・amber・保存可) |
  | ハード制限 (<17.5) | `健康的な目安を大きく下回るため、この値では設定できません` (保存不可) |
  | 初回ヒント (任意) | `数値はタップで変更できます` (初回 goal-edit 表示時に一度のみ) |
  | ステッパー a11y | `0.5kg 減らす` / `0.5kg 増やす` (ボタン表示は `−` / `＋`) |
- 手入力で確定した値も**凍結アンカー**として扱い、以後の体重変化で動かさない (上記 commit 規則と同じ)。
- **スコープ外 (バックログ)**: 目標BF% / カロリーの手入力、「○月○日までに」期限逆算モードは本 v1.7 には含めない (§13 / Later)。

**維持 (maintain) への切替**
- 維持切替時、基準体重を**現在体重へ無言固定しない**。直前に減量/増量ゴール (`targetWeightKg` アンカー) が存在し、**現在体重がまだそのゴールに到達していない**場合、**一度だけ確認 UI** を出す:
  - ① 「減量を続ける (目標 例 73kg のまま)」 → **目的は `lose` のまま据え置き**。維持には切り替えない (デフォルト)
  - ② 「今の体重 (例 77kg) を維持に切り替える」 → 目的 = `maintain`、アンカー = 現在体重
- 「当初ゴールまで整えてから維持」という中間状態は**作らない**。ゴールを目指す過程はあくまで `lose` (減量) として扱う。
- 現在体重が既にゴール到達済み、または直前ゴールが無い (初回から維持) 場合は確認なしで現在体重をアンカーとする。

**受け入れ条件**
- 目的・ペースを変えずに goal-edit を保存しても、目標体重が変化しない。
- 体重を記録しても保存済みの目標体重が変化しない。
- 減量ゴール未到達で維持を選ぶと「減量継続 / 現体重で維持」の確認が出て、当初ゴールを無言で失わない。
- 進捗は推移チャート + 目標ラインで表現し、目標は時間が経っても揺れない。
- 目標体重を数値で手入力でき、その値がアンカーになる。健康レンジ外は警告が出る。手入力しても目標カロリーは危険値にならない (行き先のみ変更)。

#### 6.5.0 入力経路のスコープとベンチマーク方針 (v1.6)

##### MVPスコープ
MVP では Quick Log の **9 ボタン × Identity ツリー (長押しで階層展開) × 自動学習 (§6.5.1)** のみで食事入力体験を構築する。Identity 全件検索バーや代替入力経路 (バーコード / 写真AI / 音声 / 自然言語等) は [ROADMAP.md](./ROADMAP.md) で段階導入する。9 ボタンで見つからない Identity に当たった場合のフォールバックは「**長押し → 階層展開**」で吸収する。

##### ベンチマーク方針: あすけん主軸 + 解釈A (v1.6)
検索/入力体験の充実度は、**国内シェア最大の競合「あすけん」を主軸ベンチマーク**に据える。ただし「DB件数で勝負しない」を原則とし、以下の **解釈A** を方針として確定する。

- **コア導線は変えない**: 9ボタン × Identity ツリー × 自動学習が主導線。検索は「ボタン+長押しで届かなかった時の最後の砦」として位置付ける。コア体験の軽さを毀損しない設計を最優先する。
- **検索DBの規模感**: 1,000〜3,000 Identity + ブランドチップ数百〜千件で十分とし、あすけんの 10万件規模は追わない。
- **判定指標**: ユーザーが「あすけんなら載っているのに、ここにはない」を感じる頻度を `quick_log_unfound_event` (§10.2.1) で計測し、しきい値超過時のみ Identity DB を拡張する。
- **拡張優先順**: 「あすけんで頻出 × 自社未収録」リストを起点に、日常的な日本食 / コンビニメニュー / 外食チェーンメニュー / 加工食品の順で投下する。

##### 9ボタンと検索の役割分担
| 経路 | 役割 | カバー想定 |
|------|------|-----------|
| 9ボタン × Identity ツリー | 主導線 | 日常的な食事の 70〜80% を1〜2タップで完了 |
| 長押し → 階層展開 | 第1フォールバック | ツリー内で見つかるが頻度学習に乗っていない Identity |
| 検索バー (Next で再有効化) | 第2フォールバック (最後の砦) | ツリーに含まれないブランド・商品名・特殊な料理 |
| バーコード (Next 後半) | 補助 | パッケージ食品・飲料 |

##### 計測と判断
9 ボタン × 自動学習だけでは届かないケースの規模は §10.2.1 の補助指標 (`quick_log_unfound_event` / `manual_correction_rate` / `long_press_drilldown_rate`) で継続計測する。検索バー再有効化後は `identity_search_usage_rate` も追加計測し、検索→ログ完了率を四半期単位でレビューする。


#### 6.5.1 食事傾向の自動学習

**方針の転換 (v1.2)**:
従来のオンボーディング内での食事パーソナライズ取得は廃止し、**ユーザーの食事ログから自動的に傾向を導出する** 方式に変更する。

**理由**:
- 食事の傾向はユーザーに質問しなくても記録データから推定できる (ログタイムスタンプ・選択食品・量)
- オンボでの質問は「仮説」にすぎず、ログ2〜3日分あれば実データが優先されるべき
- オンボ長さを圧縮することで完了率を改善 (13 → 10ステップ)
- PRD §3.1 方針 (「ユーザーの記録行動で成立する」) と整合

**自動学習の入力 (ログデータ)**:
- 食事ログのタイムスタンプ (朝/昼/夕/間食の分布)
- 選択された Dish / Food の頻度
- 各ログの量

**自動学習の出力 (Quick Log最適化)**:
- Quick Log 初期タブ順 — 各時間帯で頻出カテゴリを優先
- 食材/料理候補の優先表示順 — 頻度順で並び替え
- 量の初期値 — 直近ログの中央値を採用し、量チップ「いつもの」として表示 (下記「量の初期値 (いつもの量)」)
- おすすめチップ/ショートカット候補 — 実績ベース

**初日体験 (ログ0件時) のフォールバック**:
- デフォルト順 (万人向け一般的なタブ順)
- 量は中央値 (ふつう相当)
- 初回ログ完了後、翌日以降から徐々に学習結果が反映される

**量の初期値 (いつもの量) (v1.11)**:

うどん・そばに限らず、**全 Identity・全単位 (g / ml / 個 / %) に同じ規則**を適用する。

- **学習の単位**: 記録先 Identity × 種類 (Attribute)。種類ごとに量の基準が違う (Attribute 別 AmountSpec 上書きがある) ため、種類をまたいで流用しない
- **入力**: その組み合わせの記録済みログ (`FoodLog`) の量。⭐️履歴ではなくログ本体を見るので、**保存後の編集 (量の修正) も学習に反映される**。単位が現在の AmountSpec と合わないログは除外 (旧 serving 値は % へ換算)
- **算出**: 直近 **5件** の中央値 (下側中央値 = 実際に記録された値のどれか。丸め不要で、必ず入力可能な値になる)
- **採用条件 (合意判定)**: 直近5件のうち **3件以上が中央値の ±15% 以内**。満たさなければ既定値のまま。1回の特盛りや気まぐれで既定値が動かないようにするため
- **追従**: 窓が直近5件なので、食べ方が変われば数回の記録で新しい量に追従する。リセット操作は設けない
- **表示**: 学習値が既定値と異なる場合、量チップに **「いつもの」** を量の大小順の位置へ追加し、シートを開いた時点で選択済みにする。チップに数値は書かない (選択すれば下の量欄に出るため)。学習値が既存チップの値と一致する場合は「いつもの」を足さず、そのチップを選択済みにする
- **適用箇所**: 量シートの初期値 / Identity 切替時 / 種類切替時 / シートを開かずに1タップで記録する経路。プリセット (検索の組み合わせ候補) が量を指定している場合はそちらを優先。編集時は「いつもの」チップを表示するが、量は保存済みの値を復元する (編集中のログ自身は学習から除外)
- **計測**: 量シートで量を変えてから保存した率 (`manual_correction_rate`) が Identity 単位で下がること

**学習のリセット/手動調整**:
- My Status から「学習をリセット」可能 (必要に応じてP2で実装)
- ユーザーが並び順を手動変更した場合は手動優先

**受け入れ条件**:
- ログ蓄積後、Quick Log のタブ順・候補順・初期量がユーザーのログに合わせて変化する
- 同じ Identity × 種類を直近5件中3件以上ほぼ同じ量 (±15%) で記録すると、次回その量が初期選択され「いつもの」チップが出る
- ログ0件の初日はデフォルトで動作する
- オンボーディングで食事に関する質問は一切行わない

#### 6.5.2 記録時の安心ヒント (v1.14)

**背景**: ユーザーFB「記録するとき、20〜30kcalの誤差でも差があると感じてしまう」。詳細シートのフッターは kcal を 1kcal 単位で出すため、「どこかに正しい値がある」「それを選ばないといけない」と感じさせやすい。実際には、食品の値・盛りつけ・消費側の推定 (TDEE) のどれも数十kcal以上の幅を持っていて、20〜30kcal の差は結果を左右しない。**それより、正確さを気にして記録が重くなり、続かなくなるほうが影響ははるかに大きい**。ブランドの「ざっくりで、いい。」(VOICE.md) を、記録の瞬間に体験として伝える。

**方針**: 長く説明して説得するのではなく、迷いやすい瞬間に一言だけ添える。「雑なアプリ」に見えないよう、差の大きさを身近な量に置き換えて**根拠のある安心**にする。

**仕様 (最小版)**:
- **出す場所**: 詳細シート (`IdentityLogSheet`) のフッターの kcal プレビューを指す吹き出し (`Callout`)
- **出すタイミング**: シートで**初めて kcal が表示されたとき** (保存前)。不安が生まれるのは記録の前なので、保存後ではなく保存前に置く
- **頻度**: **生涯1回**。**表示した時点で表示済み**とする (`settings.roughHintSeenAtISO`)。そのシートを開いている間は × で閉じるまで出し続ける。既存ユーザーも未表示扱いなので、次に詳細シートを開いたときに1回出る
- **操作を止めない**: 吹き出しは操作をブロックしない。チップ選択などシートの操作はそのまま続けられる
- **出すまでの待ち**: シートの入場アニメーションが落ち着いてから (約0.7秒後) 出す
- **編集時は出さない**: 保存済みログの編集 (`editingLogId` あり) では出さない。初めての「記録」体験に絞るため
- **文言** (ja / en):
  - 「20〜30kcalは、ごはんひと口くらいの差。」
  - 「ざっくりでも、記録を続けるほうがずっと大切です。」
  - 根拠: 精白米ごはん約20g ≈ 30kcal (日本食品標準成分表 めし 156kcal/100g)。規制上の許容差 (食品表示 ±20%) は「表示が当てにならない」という新たな不信を生みうるため文言に使わない

**今後 (FB待ち)**: 迷いの行動 (同じバケット内の候補や量チップの行き来、保存後の小さな修正) を検知し、**比べている候補の kcal 差が実際に小さいときだけ**場面に合わせた一言を出す案がある。初回ヒントへの反応と今後の FB を見て判断する。

**受け入れ条件**:
- 詳細シートで初めて kcal が表示されると、フッターの kcal を指す吹き出しが出る
- 一度表示済みになると、以後どのシートでも出ない (アプリ再起動後も)
- 吹き出しの表示中もチップ選択・保存ができる
- 編集モードでは出ない

#### 6.5.3 ⭐️タブ — ピン留め優先 + 自動で補充 (v1.17)

> **状態 (2026-10-26): 実装済 (コード有・到達可能) / 実ユーザー未検証 / ネイティブ実機未確認。** 起点: [PROBLEMS.md](./PROBLEMS.md) P-007。2a (2026-10-25) でピン留め → 自動の並び (区切りなし)・記録シートの ⭐️トグル・編集ページ・出現条件・タップ内訳の計測、2b (2026-10-26) で My食品が1件以上のときの2段レイアウトを実装したが、同日に**やめて** (v1.18)、My食品もお気に入りに入れる形にした (下の「レイアウト」)。

**背景**: 「自分がよく記録するものを自分で整理したい」という声がテスターから多い。自動のランキングだけでは次の4つに応えられない。

1. 開き直すたびに順位が変わり、位置を覚えられない (記録直後の並べ替えは避けているが、次にタブを開けば変わる)
2. 一度きりの食事が上位に居座り、消せない
3. 回数の少ない新しい習慣 (最近始めた朝のプロテインなど) を置けない
4. タブの見た目は星 (= 自分で選んだもの) を約束しているのに、中身は自動の頻度順

**方針**: 自動をやめるのではなく、**ユーザーが決めたものを先頭に固定し、残りの枠を自動が埋める**。何もしなくても今まで通り使え、整えたい人だけが整えられる。

**レイアウトは1つ — 名前だけのピルを折り返して並べる** (2026-10-26 変更。v1.18):
- お気に入り (食材・料理の Identity と My食品) → 自動で補充、の順に、**名前だけのピル**を折り返して並べる。見出しは付けない。末尾に「編集」(plain のピル) を1つだけ置く
- My食品のピルも、食材のピルと**見た目を変えない** (自分で名前を付けたものなので名前で分かる。ピン留めと自動を区切らないのと同じ考え方)
- タップ・長押しはピルの種類によらず同じ考え方: 食材 = いつもの量で記録 / 量シート、My食品 = **保存した値 (100%) で記録** / 量の記録シート
- **当初案 (2026-10-25) との差分**: My食品が1件以上のときは2段 (上段 = お気に入りのピル1行の横スクロール、下段 = 最近使った My食品4件のリスト + 「すべて N件 ›」) にしていた。実装して見たら、見出し2本・リンク2本・行ごとの量と kcal と「+」で文字だらけになり (P-007 Story g)、9ボタンの高さ (標準幅で184px) にも収まらなかった (約270px)。上段の横スクロールも、ホームの日付ページャーの横スワイプと操作が重なる。**My食品もお気に入りに入れられるようにすれば、下段のリストは要らなくなる**ので、2段をやめた。当初「ピン留めのみにすると、保存直後に下段が空になり『残したい』に応えられない」としていた点は、保存したものが検索ページの「最近」と My食品ページ (倉庫) に残ることで応える (⭐️は自分で選んだものを置く棚)
- My食品ページ (倉庫) への入口は**ホームの⭐️には置かない** (§6.5.4)。「0件でも『My食品を追加』のエンプティステートを出す」案 (2026-10-25 保留) も、2段をやめたので対象が無くなった

**並び**:
- 先頭に**ピン留め** (ユーザーが決めた順で固定) → 続けて、残りの枠を**自動ランキング** (現行の `rankFrequentIdentities`) が埋める
- 自動分から、ピン留め済みのものと「表示しない」にしたものを除く (**同じものを二度出さない**)
- ピン留めと自動分は**区切らず続けて並べる** (2026-10-25 変更。当初は細い線で区切る案だったが、実装して触った人が「線が何を示すのか全然分からなかった」。星の目印も付けない。ピン留めかどうかは、先頭に並ぶことと編集ページで足りる)。見出しも付けない
- 表示枠は現行どおり (9ボタングリッドの高さに収まる行まで)。**ピン留めが枠を埋めたら自動分は出ない**
- ピン留めが枠を超える場合は、**ピン留めは枠を超えても全部出し (上限は設けない)、枠の高さは固定したまま、超えたぶんは縦スクロールで見る** (2026-10-26 変更。2026-10-25 は「超えたぶんだけ縦に伸ばす」と決めたが、お気に入りを増やすほどホームの高さが増えていくのは避けたい、という指摘で固定にした。**横スワイプで頁を分ける案は採らない**: ホームの日付ページャー (横スワイプで日が変わる) と操作がぶつかる)
- 並び順は現行どおり**タブを開いたときに確定**し、表示中は動かさない (記録直後に押したピルが指の下で動かないように)

**ピン留めの単位**:
- まず **Identity 単位**。種類 (Attribute)・調理法・量までの保存は将来の拡張とする。旧 `FrequentGrid` で「組み合わせ単位は情報量が多すぎる」というFBがあり、現在のピルが名前だけなのもそのため
- タップ = 「いつもの量」で記録、長押し = 量シート (現行どおり)。**ピルの長押しはピン留めには使わない**
- ピン留め対象は **Identity と My食品** (2026-10-26 変更。当初は Identity のみで、My食品は⭐️の下段のリストに出していた)。My食品は保存した値ごと (種類・量の区別は元から無い)
- **自動の補充は Identity のランキングだけ**。お気に入りに入れていない My食品は⭐️に出ない (検索ページの「最近」と、名前の検索で出る)。トリガー: My食品の記録が多いのに、お気に入りに入れている人がほとんどいない → 最近使った My食品を自動の補充に混ぜるかを検討
- **保存しただけではお気に入りに入れない**。保存スイッチは初期 ON なので、自動で入れると一度きりの食事で⭐️が埋まる
- Identity 辞書から消えた Identity や、削除した My食品がピン留めに残っていた場合は、**黙って表示から除く** (My食品の削除ではピン留めからも外す)

**操作 (普段の画面には操作を増やさない)**:

| 操作 | 場所 |
|---|---|

- ⚠️ `/dev` ルートは本番ビルドでは開けない (検索ミスログを設定に移したのと同じ理由)。テスター端末の名前を集めるには、「見つからなかった食品」と同じく**ユーザーが押したときだけ共有する導線**が要る。名前は自由文で食事内容を含むため、共有するのは**画面に出ている名前と件数だけ**とし、記録の本体 (数値・日時) は含めない。**導線は入れる (2026-10-25 決定)**。最小の形は、設定の「見つからなかった食品」(§6.8) と同じ作りで、画面に出ている My食品の名前と件数 (および DB に着地するか) を、ユーザーが押したときだけ OS の共有シートで送る。置き場所と文言は実装時に決める。MVP の初回出荷に含めるか、2b の直後に回すかは実装セッションで工数を見て決める

**検証の前提 (未検証)**:
- 要望者が数値で入れているものが**市販品 (成分表示あり) 中心**なら、根本解は brandChips (P2-S4) / バーコード (P2-S5) の可能性がある。**自炊・外食中心**なら My食品が正解
- 判断は、テスターの直接入力のうち**名前つきで記録されたもの**を見て行う。名前は FoodLog に残っているが、いまはテスター端末の中にしかない。開発者が見る経路は上の共有導線か、テスターへの聞き取り

**受け入れ条件**:
- 数値入力ページで名前を入れると「My食品に保存」が ON で出て、そのまま記録すると My食品に残る。スイッチを外して記録すると残らない。名前が空なら保存の選択肢が出ない
- 同名で値が違うとき、上書きか別名かを選べる。値も同じなら何も聞かれない
- 検索ページ (入力前) に「最近」(検索経由のもののみ)・「My食品 N件 ›」・「数値で入力する」が並ぶ。9ボタン・⭐️経由の記録は「最近」に出ない
- 文字を入力したとき、My食品が別の塊で出て、Identity の順位は My食品の有無で変わらない
- My食品ページは全件を最近使った順で出し、並べ替え・スワイプ・編集モードを持たない。行の右の「+」(外枠つき) で、押すと記録の画面 (量) が開くと分かるようにする。行のタップは編集ページ。検索結果の My食品の行は、タップも「+」も記録シート (検索は記録のための画面のため)
- 「+」→ 記録シートで、保存した値 = 100% から%で量を変えて記録できる (−/＋・数値入力・チップ)。保存値は変わらない。記録シートに「編集」は無い
- 記録シートの「値を直す」で、kcal・PFC をその場で直して保存できる。保存すると記録シートのプレビューに反映され、過去の記録は変わらない
- 行タップ → 編集ページ (下層ページ) で名前・数値を直せ、お気に入りに入れる/はずせ、削除できる。編集・削除しても過去の記録の数値・名前は変わらない。削除すると⭐️のお気に入りからも消える
- 編集ページと削除の確認に「これまでの記録は変わりません」が出る
- 登録済みでない過去の直接入力を開くと「My食品に保存」が出る
- 名前を入れたとき、既存の検索で確実な一致 (層1) がある場合だけ「すでにあります ›」が一行出る。タップでその Identity の記録シートへ移れ、無視してそのまま記録できる。層1でなければ出ない。同名の Identity があっても保存は止まらない
- 保存時に「My食品として保存した数」と「そのうち層1で着地した数」が `/dev/diagnostics` で読める。My食品の名前は、現在の検索で DB に着地するかで分けて集計される
- 週次リキャップで kcal・PFC の合計に含まれ、食材の発見・豆知識には出ない

### 6.7 Review (振り返り)

#### 6.7.1 設計原則
記録継続のモチベーションを保つため、過去の自分の積み上げを **軽量に振り返れる** UIを提供する。長期傾向分析や比較レポートは引き続き Out of Scope (§4.2) とし、本セクションでは MVP 範囲の最小限のレビュー体験のみを定義する。

#### 6.7.2 Home横スワイプ (過去日表示・遡及記録)
- Home画面を横にスワイプすると、当日 ← → 過去日に切替わる
- スワイプ可能範囲は **オンボーディング完了日 〜 今日**
- ヘッダー中央に現在表示中の日付ラベル ("今日" / "昨日" / "4/22 (火)") を表示
- 過去日ページの動作:
  - StatusCard (その日の集計) を表示
  - **直近7日以内**: Quick Log を表示。タップで **その日付にログを追加** (timestampは過去日付の現在時刻)。インラインで編集可能なログリスト (タップで編集、削除ボタン)。「○月○日に記録します」のヒントバナーを表示
  - **7日より前**: 読み取り専用リスト。新規追加・編集不可。「7日以上前の日付には記録を追加できません」と表示
  - Today's log bottom sheet は当日表示時のみ (過去日はインライン)
- 当日ページは従来通り (StatusCard + Quick Log + Today's bottom sheet)
- 過去日への記録の上限日数は定数 `MAX_PAST_LOGGING_DAYS = 7` で管理

#### 6.7.3 実績画面 (/stats)
Home ヘッダー右上の実績アイコン (グラフ) からアクセス。週/月のセグメントコントロールで切替。

**週ビュー**
- 週ヘッダー: ← `M/D – D` →。オンボ完了週より前は遡れない、来週は進めない
- **日別 kcal 棒グラフ** (7本)。目標カロリーを点線で重ねる
- **週平均カード**: 平均 kcal/日、平均 PFC、記録した日数 (例 5/7日)
- **日別リスト**: 各日 "M/D (曜) · ◯◯◯ kcal · P◯ F◯ C◯"。タップでHome のその日へ移動

**月ビュー**
- 月ヘッダー: ← `YYYY年 MM月` →
- **カレンダーグリッド** (7列 × 6週、Sunday-start)
  - 各セル: 日付番号 + その日の kcal に比例する円
  - 円の色: 目標±10%内=サージュ系、未達=薄色、超過=暖色
  - 記録のない日は円なし
  - 翌月にまたがるセルは薄表示、未来日はタップ不可
- **月平均カード**: 平均 kcal/日、平均 PFC、記録した日数

#### 6.7.4 導線変更
Home ヘッダー右上の **設定アイコンを実績アイコンに置き換え** る。設定画面へは My Status Hub から遷移する (Progressive Disclosure に整合)。

#### 6.7.5 週次振り返り (/weekly-recap) — 発見プール方式 (v1.8)
直近の完了週 (月〜日) をタップ送りのストーリーで振り返る。`StatusCard` の teaser から起動。

**課題 (v1.8 で是正):** 旧構成は6枚固定 (表紙 → 記録日数 → 平均kcal → PFC → アドバイス → 締め) で、比較対象が「目標」のみだった。食習慣が安定しているほど毎週ほぼ同じ内容になり、「発見がない」状態だった (PFC は最大乖離の1軸だけを出すため同じ軸に張り付き、候補食材も全履歴の頻度上位で固定)。

**設計原則:** 発見 = 「**いつもの自分との差**」か「**はじめて**」。毎週の固定部は短い事実に留め、可変の「発見スライド」を**候補プールからスコア選抜**する。

**各カードの役割 (v1.15):** カードごとに「何が分かれば、食生活を変えるきっかけになるか」を先に決め、出す情報はそこから選ぶ。良し悪しは言わず、**気づきと、次に選ぶときの手がかり**を渡す。

| カード | 伝えること | ユーザーが分かること | 改善へのつながり |
|---|---|---|---|
| 表紙 | 先週をふりかえる時間 | — | — |
| 記録日数 | 先週、記録が残っている日数 | 以降の数字が何日分の記録にもとづくか | なし (少ない週を責めない。数字の確からしさの前置き) |
| 平均kcal | 1日あたりの量と、目標・いつもとの差 | 量が目標やいつもと比べてどのくらいか | **量**の調整 (多め/少なめを自覚する) |
| いちばん多く | 先週の食事の軸になった食材 | 自分の食事で何が大きいか | 毎日食べるものの性質を知る (豆知識) |
| はじめて / ひさしぶり | 食べたものの幅 | 新しく・久しぶりに食べたもの | 食の幅への気づき。その食材の性質を知る (豆知識) |
| もと (macroSources) | ある栄養素が、どの食べものから来ていたか | **同じ栄養素でも、どの食べものから取るかで中身が変わる** | **供給源の選び方** (脂質なら脂の種類、たんぱく質なら質や一緒にとれるもの、炭水化物なら食物繊維や水分)。豆知識はこの話題に絞る |
| PFC インサイト | カロリーの内訳 (P/F/C の割合) で、目標の割合とのずれがいちばん大きい栄養素 | 配分の傾向 (量ではない) | **配分**の調整 |
| アドバイス | そのずれを調整できる食材 | 次に何を選べばいいか | 具体的な選択肢 (増やす/置き換える)。食事として選ぶ食材に限る (調味料・お菓子・飲み物・加工肉は出さない) |
| 締め | ざっくりでも続けること | — | 継続 |

- 豆知識は、そのカードで伝えたいことに沿うものだけを出す。合うノートが無い週は**何も添えない** (無理に話題を変えない)
- **置き換えの規則 (「多めの週」)**: 先週の記録に置き換え元があるときだけ、置き換え先を出す。履歴に無ければ何も出さない。表は `utils/weekly-recap.ts` の `SWAP_RULES`
  - 脂質: 牛・豚 (高脂 / 普通脂)・ベーコン・ソーセージ → 赤身肉 / 鶏もも → 鶏むね / チーズ → チーズ (低脂) / 油揚げ → 豆腐 / クリーミー系の副菜 → 煮物・和え物 / パン (リッチ) → パン / 脂質の多い麺料理 (ラーメン・つけ麺・焼そば・パスタ・天ぷら麺など1食15g以上) → そば・うどん
  - 炭水化物: ごはん (白米) → 玄米 / パン (食パン) → 全粒・ライ麦 / うどん → そば / パスタ → 全粒粉 / シリアル → オートミール / 菓子パン → パン / ジュース → 果物
  - 炭水化物の置き換えは、**量はほとんど変わらない** (玄米ごはんの炭水化物は白米と同程度)。だから「少なくなる」とは言わず、精製の度合いや中身の違いを豆知識で伝える。すでに玄米などを選んでいる人には出さない (記録の種類を見る)
  - 食物繊維は、八訂では白米ごはん (1.5g) と玄米ごはん (1.4g) の差が小さい。玄米の豆知識は、差がはっきりしているマグネシウム・ビタミンB1で書く
  - 置き換え先は許可リストとは別に、この表で決める (麺料理は料理なので許可リストに入らない)
- アドバイスの候補は**勧めてよい食材 (許可リスト) だけ**。食べた事実はどの食材でも映すが、勧めるのは一般に体に良い・少なくとも悪くない食材に限る。料理は作り方や店で中身が変わり勧める根拠を持てないので入れない
- アドバイスの豆知識も、その栄養素の話 (`topics`) のノートに限る (「なぜこの食材が候補か」を支えるため。ナッツのビタミンEの話は「脂質を増やしたいときは」に添えない)
- 「もと」カードの豆知識は、ノートの話題 (`NutritionNote.topics`: protein / fat / carbs) がその週の栄養素と一致するものに限る。カードに並んだ食材の順 (割合の大きい順) に探す。同じ週の他のカードと同じ文面になるときは出さない
- 「もと」カードでは不足を言わない。並ばなかった食材 (例: 魚が出てこない週の n-3) の話はしない。単押しの記録で不足を言わない方針 (§10.14) に従う
- 不飽和脂肪の話は「足すほど良い」と読める書き方をしない (便益は主に飽和脂肪との置き換えから来る。US-food-db-design.md の `unsat_fat`)

**構成 (6〜7枚):**
1. 表紙 (固定)
2. 記録日数 (固定) — 補足に「その前の週は N日」(方向語は付けない。少ない週を責めないため)
3. 平均kcal (固定) — 補足に「前の4週の平均」(記録7日以上あるとき)。±10% 以上ずれた週のみ「いつもより 多め/少なめ」を添える
4. 発見スライド × 最大3枚 (可変・下表から選抜)
5. 締め (固定)

**発見の候補 (既存 FoodLog フィールドのみで成立。NutritionTag 不要):**

| kind | 条件 | 見せ方 |
|---|---|---|
| `topFood` いちばん多く | 週内で同じ Identity が3回以上 | 「いちばん多く記録したのは ◯◯ (N回)」。**前週と同じ食材なら低スコア** |
| `newFoods` はじめて | 週内に初登場の Identity (記録が前週以前にもあるユーザーのみ。初週は全部が初登場になるため出さない) | 最大3件 |
| `comebackFoods` ひさしぶり | 週内に記録され、その直前の記録から28日以上空いている | 「◯週ぶり」を添えて最大3件 |
| `macroSources` もと | 常に候補 (その週に対象栄養素が1g以上ある)。対象の栄養素 (P/F/C) は週ごとにローテーション | 「先週の◯◯は、おもにこの食べものから」上位3件と全体に占める割合 (約◯%)。記録ごとの `macro` を Identity 別に合算するだけで、新しいデータは不要。**評価しない** (多い/少ないは言わず、内訳の事実のみ)。Identity を持たない旧ログはカテゴリ名でまとめる |
| `macro` PFC | P/F/C のエネルギー比が、目標の比率から15%以上ずれた最大1軸 (v1.15 で量→割合に変更) | インサイト + アドバイスの2枚。**同じ軸・方向が続く週は連続週数で出し分け**: 1週目=通常 / 3週目=「3週続けて少なめ」(VOICE.md の例文どおり) / それ以外の連続週は休ませる (他に発見が無い週のみ出す) |

**豆知識の添え方 (v1.9):** `topFood` / `newFoods` / `comebackFoods` のカードには、掲載食材のうち最初に `nutritionNotes` を持つ1件を、**出典つきで**カード下部に添える (週ごとに決定的に選ぶ。複数ノートを持つ食材は週で切り替わる)。豆知識は「食べたもの」について語るときにいちばん読まれるため、食べていない食材の話 (アドバイス候補) だけに置かない。ノート未整備の食材はカードだけ出し、ノート欄は出さない。`macroSources` のカードにも、話題の合う豆知識を添える (v1.15、上の「各カードの役割」)。

**選抜ルール:** 各候補にスコアを付け、枠 (カード3枚分、`macro` は2枚分) に高い順で詰める。表示順は物語の流れを優先して固定 (topFood → newFoods → comebackFoods → macroSources → macro)。**選抜は記録データだけから決定的に求める** (同じ週なら何度開いても同じ内容。表示履歴は永続化しない)。
- アドバイスの候補食材は、該当する履歴が4件以上あるときは週ごとに3件ずつローテーションする

**トーン (§9.1 / VOICE.md):** 差は「多め/少なめ/◯週ぶり/はじめて」の事実のみ。「増えた=えらい」「減った=だめ」の評価語は使わない。スコアや達成率は出さない。

**スコープ外 (後続):** 食事のリズム (平日/週末・時間帯) / からだ (体重・運動) / 質の「鏡」(NutritionTag) は、同じプールに候補を足す形で拡張する。直近4週との比較は「いつも」の基準を作るためのものであり、§4.2 の比較レポート・長期傾向分析には当たらない。

### 6.8 フィードバック導線 (設定)

設定の「フィードバック」区分に、**ユーザーが自分の意思で開発者へ送るもの**をまとめる。「設定」(アプリの振る舞いを変える) とも「情報」(読むだけ) とも性格が違うため独立させる。

| 行 | 中身 | 届き先 | 備考 |
|---|---|---|---|
| 見つからなかった食品 | 端末に貯まった未ヒット語と回数 (§10.2.1)。共有前に編集・削除できる | 開発者 (OS の共有シート) | 件数を行に添える (0件なら出さない)。食事の記録は含めない |

- **メール版をやめた理由 (2026-10-04 非表示 → 2026-10-24 フォームで復活)**: メールアプリで送る形は ①送り主のメールアドレスが届く (データセーフティでは「収集しない」と申告) ②手間が重い ③受信箱に混ざり種類で分けられない、の問題があった。当初の代替案 A. Google フォーム は、FB の置き場 (Notion) に直接入る **Notion の匿名フォーム**に置き換えた。Layer 2 のときに **B. アプリ内の入力欄 + 自前の受け口** (見つからなかった食品も同じ受け口に載せる) を検討する
- 種類の整理: 「アプリが貯めてユーザーは送るだけ」(見つからなかった食品) / 「ユーザーが書く・非公開」(フォーム) / 「ユーザーが書く・公開」(ストア)
- **自動送信は将来**: 解析サービスへの自動送信 (KPI計装 Layer 2) を入れたら、見つからなかった食品はユーザーが送る必要がなくなる。その時点で行を外し、設定 > データ に「利用状況を匿名で送る」の切替を置く (プライバシーポリシー・データセーフティの改訂が前提)

## 9. 非機能要件

### 9.1 UX
- 片手操作前提、**1画面1入力原則** (モダン健康アプリ標準パターン)
- キーボード入力は returnKey → 自動次へ、タップ選択は選択即次へ
- 数値・説明文・ビジュアルで補完
- **中立トーン**: 価値判断や羞恥を生む命名・表現を避ける
  - 9分類に固有名称 (「スリム」「隠れ脂肪」等) は **付与しない**
  - 軸ラベル (脂肪×筋量 · 少なめ/ふつう/多め) のみで表現
- 各画面のサブタイトルに **「→ 〇〇の計算に使います」** 形式で用途を明示 (データ要求の根拠を見せる)
- **結果フィードバック**:
  - 現在体型選択時: 派手な演出なし (静的表示)
  - 目標体型・目標確定時: ポジティブな演出を許容 (具体は TBD)
- 進捗表示は **Phase単位** (例: "Phase 1 · 3/5") で残タスク感を軽減
- **Progressive Disclosure** (§6.6): 情報は必要な粒度でだけ露出する。ユーザー編集不要なデータ (食事傾向の自動学習結果など) は UI に出さない
- 編集UIは基本 **ボトムシート** で完結。重い編集 (プロフィール等) のみ別画面プッシュ

### 9.2 Performance
- 現在体型再計算はほぼ即時
- SVG読み込みで重くならない

### 9.3 Reliability
- 途中離脱時も再開可能
- 保存失敗時は再試行 or 一時保持

### 9.4 Accessibility
- 色依存しない選択状態
- 文字サイズ可変対応
- 音声読み上げラベル
- テキスト説明併記

### 9.5 Privacy / Compliance
- 取得データは最小限
- 利用目的明示
- 編集・削除可能
- 健康関連データとしての慎重な取り扱い

#### ロードマップ判断ルール (v1.6 更新)
- **検索系 (P2-S1〜S3) は条件判定なしで Next 確定実装** — v1.6 でベンチマーク方針が解釈Aで定まったため、`unfound_event` 値に依らず投下する

- **P2-S5 (バーコード)**: コンビニ・パッケージ食品ユーザーの比率が高い場合は P2-S1〜S3 と並行で先行投入
- **P2-S7 (My食品)** (v1.17): 要望者が数値で入れているものが市販品中心なら、根本解は P2-S4 / P2-S5 の可能性がある (§6.5.4 の「検証の前提」)。名前つきの直接入力を見て判断する
- **P3-A (写真AI)**: on-device モデル成熟度と外部 API コストを見ながら判断 (大規模投資判断)

## 14. デザイン/開発への引き継ぎメモ

**デザイン**
同一シリーズ比較性が最重要。個別イラストの完成度より、18体を並べたときの一貫性が優先。M5/F5はシリーズの中点であり、そこから端点と中間を差分展開する前提で進める。

**開発**
体型ロジック・目標提案ロジック・Quick Log初期表示ロジックを疎結合に保ち、ロジック差し替えやABテストがしやすい構造で実装する。
