# EXPERIENCE_DEPTH — 体験軸ロードマップ

> **このドキュメントの目的**: [ROADMAP.md](./ROADMAP.md) は機能追加の時系列を管理する。本ドキュメントはその補完ビューとして、**「各機能がどの体験を満たし・深めるために存在するか」** を軸に整理する。
>
> 機能の優先順位で迷ったとき、「どの体験を、どの深さまで押し上げるか」に立ち戻る拠り所として使う。
>
> - バージョン: v1.0
> - 作成: 2026-08-28
> - 関連: [ROADMAP.md](./ROADMAP.md) §3.0 (実装状況) / [PRD.md](./PRD.md) §9.1 (中立トーン) / [VOICE.md](./VOICE.md)

## コア体験の定義

アプリが提供すべき体験を6軸で定義する。機能はこの体験のいずれかを深めるために存在する。

| 体験軸 | ひとこと | KPI連動 |
|---|---|---|
| **① 記録できる** | 食べたものをすぐ記録できる | 北極星: 24h以内の初回食事ログ完了率 |
| **② 把握できる** | 今日あとどれだけ食べていいかわかる | D7/D30 リテンション |
| **③ 振り返れる** | 先週の食生活を自分なりに振り返れる | 週次アクティブ率 |
| **④ 実感できる** | 体型の変化を数字と感覚で実感できる | 長期エンゲージメント |
| **⑤ 続けられる** | 記録が負担なく習慣になる | D30 / 週次アクティブ率 |
| **⑥ 納得できる** | 自分に合った目標を持てる・調整できる | オンボーディング完了率 / 長期満足度 |

> **設計の前提 (PRD §9.1)**: 評価・比較・羞恥を生まない中立トーン。体験軸はすべて「できる / わかる / 実感できる」の自己完結形であり、「すごい / 正しい / 達成できた」の外部評価軸を持ち込まない。

## 体験①: 「食べたものをすぐ記録できる」

**この体験が満たされると**: 記録のハードルが下がり、初回ログ → 継続の流れが生まれる。

### 現在地 (実装済)
- **9ボタングリッド × Identity ツリー** — カテゴリ → 食材 → 量の3ステップ
- **⭐タブ (頻度×recency ランキング)** — 使うほど自分の食材が上位に来る
- **ウィジェット (Android 5サイズ)** — アプリを開かずホーム画面から1タップ記録
- **検索 (SEARCH_SPEC v0.4)** — Identity + Attribute + Style 横断、料理名辞書222語、主辞辞書

### 次の深さ (Next)
- **Identity DB拡張 (P2-S3)** — `/dev/diagnostics` の未ヒット語データで拡張順を決定。まず `dish-vocabulary.ts` への語追加で解けないか確認する
- **カスタム食品登録 (P2-S7)** — DBにない食品を自分で登録。解釈A (検索 = 最後の砦) の補完手段として必須
- **音声入力 (P2-S8)** — 検索バーへのブリッジ。タイピングレスで「からあげ」と言える

### 将来の深さ (Later)
- **写真認識 (P3-A)** — 撮るだけで食材候補を提示。Pro 限定試験投入
- **自然言語入力 (P3-B)** — 「鶏むね150gとブロッコリー」→ 複数食材に分解

## 体験②: 「今日あとどれだけ食べていいかわかる」

**この体験が満たされると**: 「食べ過ぎた / 足りない」の不安なく、今日の食事を判断できる。

### 現在地 (実装済)
- **カロリーリング** — 摂取 vs 目標のビジュアル
- **マクロ3分割 (PFC)** — 比率と残量の同時把握
- **動的TDEE 差分方式** — 運動した日だけ目標が上乗せされる。普段の日はフラットに保つ

### 次の深さ (Next)
- **停滞検知バナー** — 2週間体重変化なし → 「ペース調整を試してみますか？」中立トーンでやわらかくヒント

### 将来の深さ (Later)
- **Adaptive TDEE** — 体重トレンドから実際のTDEEを逆算し、目標カロリーの補正を提案 (ユーザー承認型)
- **動的目標フェーズ2** — 週次の活動傾向からペース係数を自動補正提案

---

## 体験③: 「先週の食生活を自分なりに振り返れる」

**この体験が満たされると**: 記録の意義を実感でき、「続けてみよう」の動機になる。

### 現在地 (実装済)
- **週/月 統計ビュー** — `app/stats.tsx`、日別カロリー・PFC集計・体重推移
- **週次リキャップ (フェーズ1)** — `app/weekly-recap.tsx` タップ送りストーリー形式
  - スライド構成: 記録日数 → 平均kcal (+前4週との差) → 発見スライド最大3枚 → 締め
  - **発見プール方式 (2026-09-29)**: いちばん多く / はじめて / ひさしぶり / PFC (連続週で出し分け) / 栄養素の内訳 (どの食べものから取っていたか) からスコア選抜。食材系の発見には豆知識を添える。PRD v1.8-1.9 §6.7.5
  - `StatusCard` の teaser カードから起動、英語ロケール対応済

### 次の深さ (Next)
- **PFCインサイト精度向上** — `weekly-recap.ts` の高密度食材判定閾値 (protein 25% / fat 35% / carbs 45%) は暫定値。栄養学的裏取りが残タスク ([project_macro_boost_threshold_review.md](../memory/project_macro_boost_threshold_review.md) 参照)

### 将来の深さ (Later = 週次リキャップ フェーズ2)
- **質リフレクション層「鏡」** — 食品群の構成バブル。分母を出さず presence で映す (評価しない)
- **「豆知識」スライド** — よく食べた食材の組成事実。ユーザーではなく食材を語る中立トーン
- **AI 週次レビュー** — テキスト3〜5行のパーソナライズフィードバック (Pro)

## 体験④: 「体型の変化を数字と感覚で実感できる」

**この体験が満たされると**: 長期継続の理由ができ、D30+ のエンゲージメントを支える。

### 現在地 (実装済)
- **体型マトリクス** — 9分類 × 男女18体SVG。現在体型の自動推定 + 目標体型の選択
- **体重記録 + 短期トレンド** — WeightEntry 系列、週次 stats と連動

### 次の深さ (Next)
- **停滞検知バナー** — 体型変化の停滞に気づきを与える (体験②と共有)
- **目標体脂肪率手入力** — 現在は目標体重のみ手入力可。BF% も手入力できると目標の解像度が上がる

### 将来の深さ (Later)
- **目標達成セレモニー** — 現在体型 → 目標体型のシルエット遷移アニメーション
- **長期トレンドビュー** — 3ヶ月超の体重・体脂肪・体型推移 (現在 PRD §4.2 Out of Scope)
- **Adaptive TDEE** — 実測ペースと予測ペースの乖離から「なぜ痩せられないか」を可視化

## 体験⑤: 「継続できる / 記録が習慣になる」

**この体験が満たされると**: D7/D30 リテンションが底上げされ、PMF の証左になる。

### 現在地 (実装済)
- **ウィジェット** — opt-in 不要の常駐リエンゲージ。ホーム画面に置くだけで記録コストが最小化される
- **⭐タブ適応** — 使うほど自分仕様になる。継続するほど記録が速くなる正のループ

### 次の深さ (Next)
- **週次リキャップ (体験③と共有)** — 「記録した週の振り返り」が報酬になる。既実装
- **リマインダー** — 食事記録 / 体重記録。通知は基本 opt-in されないため補助扱い
- **ストリーク / 連続記録バッジ** — 中立トーン厳守 (PRD §9.1)。「3日連続で記録しています」等の事実ベース表現のみ。評価語・プレッシャーは禁止

### 将来の深さ (Later)
- **AI 週次レビュー (Pro)** — パーソナライズされた洞察で記録の意義を定期的に強化

---

## 体験⑥: 「自分に合った目標を持てる・調整できる」

**この体験が満たされると**: ユーザーが「これは自分のための目標だ」と感じ、長期で使い続ける理由になる。

### 現在地 (実装済)
- **オンボーディング** — 体型自動推定 (9分類) × Mifflin-St Jeor × 活動係数でカスタム目標を生成
- **目標体重手入力 (v1.7)** — 自動推定値をユーザーが上書き可能。固定アンカー化で目標ドリフト是正済
- **ペース・活動係数の変更** — goal-edit 画面

### 次の深さ (Next)
- **目標体脂肪率手入力** — 体験④と共有。BF% を目標に加えると意識が「体重」から「体組成」に深まる
- **期限逆算** — 「3ヶ月後に目標体重を達成したい」から逆算してペースを提案

### 将来の深さ (Later)
- **係数見直しサジェスト (下げ方向のみ)** — 実測 activeKcal が継続的に基準を大きく下回る場合に中立トーンで提案
- **Adaptive TDEE フィードバックループ** — 体重トレンドからベースTDEEを補正提案 (ユーザー承認型)

## 体験軸を使った優先順位判断フロー

```
新機能候補が出たとき:
  1. どの体験軸 (①〜⑥) を深めるか？ → 複数ある場合は主目的を1つ選ぶ
  2. その体験軸の「現在地」は十分か？ → 浅ければ先に現在地を深める
  3. 同じ体験軸の候補が複数あるとき → KPI・実装コスト・依存関係で比較
  4. 体験軸に紐づかない機能 → 技術負債 / 保守タスクとして別枠管理
```

> **注意**: 複数の体験軸に効く機能 (例: ウィジェット = ①⑤) は優先度が高い傾向があるが、「全部に効く」を理由に優先させない。主目的の体験軸が本当に浅いかを先に確認する。
