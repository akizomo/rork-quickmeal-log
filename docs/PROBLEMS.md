# PROBLEMS — 困りごとの台帳

> テスターの声 (Signal) を「型」で束ねた Problem と、その解決仮説 (Story) の台帳。運用ルールは [FEEDBACK_OPS.md](./FEEDBACK_OPS.md)。
>
> **このリポジトリは公開。** 原文・名前は書かない。根拠は FB 番号 (Notion「FB Inbox」の行) で参照し、要旨は言い換えて書く。

## 書き方

```
### P-nnn 困りごと (解決策を含まない言い方で)
- 状態: 観察中 / Story検討中 / 対応中 / 検証待ち / 検証済 / 見送り
- 体験軸: ①記録 ②把握 ③振り返り ④実感 ⑤継続 ⑥納得
- 根拠: FB-n, FB-m (n人)
- 深刻度: 止まる / 迷う / 不満
- 確信度: 発言1人 / 複数人 / 行動データでも確認
- 場面: 誰が・いつ・何をしていて困るか
- 型の広がり: 同じ型で他にどこが困りうるか
- Story:
  - a. 「〜のとき、〜したい。そうすれば〜」 — 採用 / 保留 (トリガー: …) / 見送り (理由: …)。採用なら ROADMAP / PRD の該当箇所
- 検証: 誰に・何を確かめるか / 結果
```

### P-001 数十kcalの差が気になって、記録の手が止まる
- 状態: 検証待ち
- 体験軸: ①記録 / ⑤継続
- 根拠: FB-1 (1人)
- 深刻度: 迷う
- 確信度: 発言1人
- 場面: 詳細シートで候補や量を選ぶとき、20〜30kcal ほどの差でも違いが気になり、どれにするか決めきれない
- 型の広がり: 「正確でなければ意味がない」という思い込みが、記録そのものをためらわせる。量チップの行き来・保存後の小さな修正にも同じ型が出うる
- Story:
  - a. 初めて kcal を見たとき、ざっくりでよいと分かりたい。そうすれば迷わず保存できる — **採用・出荷 2026-10-20** → ROADMAP §3.0「記録時の安心ヒント」/ PRD §6.5.2
  - b. 迷っている場面で、比べている候補の差が小さいと分かりたい — **保留** (トリガー: 別のテスターから「迷う・決めきれない」系の声が来る / 候補や量の行き来・保存後の小修正が多いと行動データで分かる)
  - c. kcal 表示を10kcal単位に丸める — **見送り** (2026-10-20。理由は記録なし)
- 検証: FB-1 のテスターに、ヒントを見たあと迷いが減ったかを聞く / 未

### P-005 プロテインが「肉魚」のバケットにあるのが腑に落ちない
- 状態: 観察中
- 体験軸: ①記録 / ⑥納得
- 根拠: FB-? (1人。番号は Notion「FB Inbox」で確認して記入)
- 深刻度: 不満
- 確信度: 発言1人
- 場面: プロテイン (ドリンク) が「肉魚(低脂肪)」のバケットに入っているのを見て、分類に違和感を持った。どこで見たか (バケット一覧か、ログのカテゴリ表示か) は未確認
- 型の広がり: 「食べ物名」のラベルのバケットに、栄養の近さで入れた別種の食品が混ざる。`protein_bar` (脂あり肉魚) も同じ。調べた範囲で肉魚でないのはこの2件のみ
- Story:
  - a. プロテインが、栄養の近いバケットに入っていると納得したい。そうすれば分類を疑わずに記録できる — **保留** (トリガー: 別のテスターから同じ種類の違和感が来る / 豆腐・納豆など別バケットのたんぱく源について「なぜここにない」系の声が来る / FB の元の場面がバケット一覧だったと分かる)
    - 検討した案: ① ラベルを「低脂肪たんぱく」「脂ありたんぱく」へ (栄養の軸と一致、英語ラベルの `Lean Protein` とも揃う。一方で「鶏むねはどこ?」の見つけやすさが下がり、別バケットのたんぱく源との境目が曖昧になる) / ② `protein_drink` を乳・大豆へ、`protein_bar` をおやつ甘飲へ移す (ラベルは変えない。栄養での分け方とは食い違う) / ③ 一覧に両方のバケットで出す (IA-identity-spec §1.3 の「primary 以外はチップに出さない」を変える必要がある。検索ではすでに両方から出る)
    - 保留の理由: ラベル変更の悪影響 (見つけやすさの低下・境目の曖昧化) が、得られる納得感を下回らないと言い切れない
- 検証: FB の元の場面を確認する / 未

### P-006 数値で入れた食品が、次に記録するとき残っておらず、毎回入れ直している
- 状態: 対応中 (Story a・d 採用・**実行順 2b 実装済 2026-10-26**、実ユーザー未検証)
- 体験軸: ①記録 / ⑤継続
- 根拠: FB-? (複数のテスターから。**FB 番号と人数は Notion「FB Inbox」で確認して記入**。「数値で入力した食品をMy食品のように残したい」という趣旨の声が多いと受け取っている)
- 深刻度: 不満 (毎回の入れ直しの手間。記録をやめたという声は未確認。Notion で確認して見直す)
- 確信度: 複数人
- 場面: 検索で見つからない食品 (または DB の値が合わない食品) を数値で入力して記録する。次に同じものを食べるとき、名前と数値をもう一度入れる
- 型の広がり: 使い捨ての入力が残らない面は、ほかにもありうる (編集中の量の「いつもの」は学習済みで対象外)。DB に無い食品が多いという別の型 (P-003 など) とは原因が違い、こちらは「見つけたあとの再利用」の問題
- Story:
  - a. 数値で入力した食品を残して、次から選んで記録したい。そうすれば毎回入れ直さずに済む — **採用 (2b 実装済 2026-10-26・実ユーザー未検証)** → PRD v1.17 §6.5.4 / ROADMAP §3.0「My食品」(実行順 2b) / PRD §13.1 P2-S7 を具体化し優先度を上げた
  - b. 市販品の成分表示ぶんは、バーコードやブランドの候補から記録したい — **保留** (トリガー: テスターが数値で入れている名前つきの食品が市販品 (成分表示あり) 中心だと分かる / 別のテスターから「商品を探したい」系の声が来る。PRD §6.5.4「検証の前提」。P2-S4 brandChips / P2-S5 バーコード)
  - d. すでに DB にある食品を気づかず My食品にしてしまうのを避けたい — **採用 (2b 実装済 2026-10-26・実ユーザー未検証)** → PRD §6.5.4「すでに DB にある食品を…」。保存は止めず、層1で着地するときだけ一行出し、診断で「着地あり / なし」を分けて数える。**頻度は予想であり未測定**
  - e. My食品に近い Identity を紐づけて、週次リキャップにも載せたい — **保留** (トリガー: リキャップから外れることへの不満が出る / 診断で「保存時に DB に着地した」割合が高いと分かる。「Identity 辞書の外に置く」合意を崩すため、実装は大きい)
  - c. g 単位で量を指定したい (100g あたりの値で登録) — **保留** (トリガー: 「1回分×倍率」では足りないという声が来る。最初は「1回分×倍率」から)
- 検証: 名前つきで記録された直接入力の中身 (市販品か自炊・外食か) をテスターに聞く、または共有導線で名前を見る → b の要否を判断 / 未

### P-007 自分がよく記録するものを、自分で選んで手元に置けない
- 状態: 対応中 (Story a 採用・**実行順 2a 実装済 2026-10-25**、実ユーザー未検証)
- 体験軸: ①記録 / ⑤継続
- 根拠: FB-? (複数のテスターから。**FB 番号と人数は Notion「FB Inbox」で確認して記入**。「自分がよく記録するものを自分で整理したい」という趣旨の声が多いと受け取っている)
- 深刻度: 不満
- 確信度: 複数人 (行動データは未取得。`tabUsageCounts.frequent` は端末内にある)
- 場面: ⭐️タブは自動で並ぶだけ。①開き直すたびに順位が変わり位置を覚えられない ②一度きりのものが居座り消せない ③回数の少ない新しい習慣を置けない ④見た目は星 (自分で選んだもの) だが中身は自動の頻度順
- 型の広がり: 「自動で出る面を、ユーザーが手で直せない」型。ウィジェットのボタン供給 (旧ランキングのまま) も同じ構造を持つ
- Story:
  - a. よく記録するものを自分で選んで先頭に置きたい。そうすれば開くたびに同じ場所にあり、すぐ押せる — **採用 (2a 実装済 2026-10-25・実ユーザー未検証)** → PRD v1.17 §6.5.3 / ROADMAP §3.0「⭐️タブのピン留め」(実行順 2a)。Identity 単位のピン留め + 残りを自動で補充
  - b. 自分でフォルダ / バケットを作って整理したい — **見送り** (理由: 9ボタン契約 (IA-identity-spec §1.1①) と衝突する。整理する人は少数で、ピン留めの並び順で足りると判断。2026-10-24)。**再検討のトリガー**: ピン留めを使っているのに「用途別に分けたい」(朝食・運動後など) という声が複数人から来る / ピン留めが多い人が診断で多いと分かる
    - 2026-10-25 に開発側で「既存の食材や料理も含めた、自分のよく使う食品をまとめたオリジナルのバケット」の要望が来そうだと予想した。**これはテスターの Signal ではない**ので根拠にしない。実際に来たときの案は ① ピン留めを名前つきのグループに分ける ② 複数品をまとめて1タップで記録する「セット」。②は「毎回同じ組み合わせを何品も記録する」という別の困りごとなので、来たら Problem を分けて立てる
  - f. My食品が0件のときも⭐️を2段にし、下段に「My食品を追加」のエンプティステートを出したい — **保留** (2026-10-25。トリガー: 数値入力は使われているのに My食品ページがほとんど開かれない / テスターが My食品に気づかない。先に要るもの: 記録せず保存だけする入口)
  - c. ピン留めに種類・量まで保存したい — **保留** (トリガー: ピン留め後に「同じ食材の別の種類を別々に置きたい」声が来る / 量シートの修正率 `manual_correction_rate` がピン留め経由で高い)。以前の FrequentGrid で「組み合わせ単位は情報量が多すぎる」FB があったため、まず Identity 単位
  - d. ⭐️の降格・撤去 — **保留** (トリガー: ピン留め導入後、`tabUsageCounts.frequent` のうち自動由来のタップがほとんど無い / ピン留めが使われていない。2026-10-24 は「ピン留めで自分のものにできるため、まず進化させる」と決めた)
  - e. ウィジェットにもピン留めを反映する — **保留** (トリガー: ウィジェットのボタンが自分のピン留めと合わないという声が来る)
  - g. ⭐️タブが一気に文字だらけになった (お気に入りのピル + 見出し2本 + 「編集」「すべて N件 ›」+ My食品の行)。もっと軽く見せたい — **保留・設計課題** (2026-10-26、2b のウォークスルーでプロダクトオーナーから。まだ案は決めていない。トリガー: 次に⭐️タブの見た目を触るとき / 実ユーザーから「⭐️が見づらい・ごちゃごちゃ」の声が来る。案の叩き台: 見出しを減らす (Overline を1本にする) / My食品の行に絵文字や色の目印を付ける / 「編集」「すべて」を末尾のピルや1か所にまとめる / 下段の件数を減らす)
- 検証: 実装後、根拠のテスターに「開いたとき同じ場所にあるか」を聞く。`/dev/diagnostics` でピン留め由来 / 自動由来のタップ内訳を見る / 未
