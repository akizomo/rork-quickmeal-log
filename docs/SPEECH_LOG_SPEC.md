# SPEECH_LOG_SPEC — 音声でまとめて記録

> 食べたものを声で言うと、カロリー付きの候補一覧が出て、確認してからまとめて記録できる機能の仕様。
> 関連: [PRD.md](./PRD.md) §13.1 P2-S8 / P3-B, [ROADMAP.md](./ROADMAP.md) レーンA, [SEARCH_SPEC.md](./SEARCH_SPEC.md) §F5 / §F8, [IA-identity-spec.md](./IA-identity-spec.md), [VOICE.md](./VOICE.md)
>
> - バージョン: v0.2 (設計のみ・実装前)
> - v0.2 (2026-10-02): 入口を SearchSheet の中 → ホームの 🔍 の隣に変更 (§3.1)。確認は常に出すことを明記 (§3.1.1)
> - 最終更新: 2026-10-02
> - ステータス: 設計完了 / 実装未着手
>
> **当初計画との差分**: PRD v1.6 では音声を「検索バーへ文字を流し込むだけ」(P2-S8) とし、複数品目への分解は AI 前提で Later (P3-B) に置いていた。
> 本仕様では **分解を AI なしの決定的処理で P2-S8 に前倒し** する。根拠は、SEARCH_SPEC v0.4 で整備した検索エンジン (層1〜4の着地保証・料理名辞書222語・主辞辞書) が「区切った1語を食べものに当てはめる」部分をすでに担えるため。
> AI (LLM) が要るのは自由な言い回し (「昨日の残りのカレーを半分くらい」) だけで、そこは引き続き P3-B に残す。

## 1. 問題と狙い

### 1.1 解決したい問題
- 9ボタンに無い食べものは検索に落ちるが、**検索はタイピング**であり「入力は面倒」に構造的に反する (ROADMAP §3.0 UX前提)
- 定食・弁当・家のおかずのように **一度に何品も食べた食事** は、9ボタンでも検索でも「1品ずつ × 品数」の操作になる

### 1.2 狙い
- **何品あっても、ひと言で記録できる**。「からあげと、ごはんと、みそ汁」→ 3件の候補 → 確認 → まとめて記録
- 9ボタンと競合しない。9ボタンは「1品を1タップ」、音声は「何品もまとめて」で棲み分ける

### 1.3 やらないこと (この仕様の範囲外)
- 自由な言い回しの解釈 (「残りを半分」「いつもの」) → P3-B (LLM)
- 写真からの推定 → P3-A
- 量の精密な読み取り (「150グラム」の g 指定は対応、「茶碗に軽く」等の比喩は対応しない)
- 音声での編集・削除 (「さっきのからあげ消して」)
- en-US ロケール (Phase 2 で対応。§9)

## 2. ユーザーストーリー

**US-1**: ユーザーとして、食べたものを続けて言うだけで、品目ごとに分かれた候補を見たい。なぜなら、1品ずつ探すのが面倒だから。

**US-2**: ユーザーとして、記録する前に、何がいくつ・何 kcal で入るのかを一覧で確認したい。なぜなら、聞き間違いのまま記録されたくないから。

**US-3**: ユーザーとして、一覧の中で違うものだけを直したり外したりしたい。なぜなら、1件の聞き間違いのために全部言い直したくないから。

**US-4**: ユーザーとして、当てはまる食べものが無かった語も、カテゴリを選べば記録できるようにしたい。なぜなら、ざっくりでいいから記録を残したいから (SEARCH_SPEC §F5 と同じ着地保証)。

**US-5**: ユーザーとして、声が使えない場面でも、聞き取った文字を直して使いたい。なぜなら、変換ミスは文字で直したほうが早いから。

**US-6**: ユーザーとして、まとめて記録したあとでも、まとめて取り消したい。なぜなら、確認を急いで押してしまうことがあるから。

## 3. フロー

```
[ホームの 🎤 タップ]
   │  権限が未許可 → OS の許可ダイアログ (初回のみ)
   ▼
[聞き取り中シート]  ← 話している文字がリアルタイムで出る (interim results)
   │  無音 1.5秒 or 「おわり」タップ で確定
   ▼
[分解・照合]  §5 (決定的処理・端末内・数十ms)
   ▼
[確認シート]  §6
   ├ 行をタップ → 種類/量を直す (IdentityLogSheet を下書きモードで開く)
   ├ 行の ✕   → 外す
   ├ 未確定の行 → カテゴリチップで着地 / 検索で探す
   ├ 「言いなおす」→ 聞き取り中シートへ戻る (一覧は捨てる)
   └ 「◯件を記録」→ まとめて記録 → ホーム + まとめて取り消せるトースト
```

### 3.1 入口 (2026-10-02 議論で決定)
- **主入口: ホームの 🔍 の隣に 🎤 (`IconButton`)**。`QuickLogSection` の `segmentRow` (⭐️タブの `SegmentedControl` + 🔍 の行) に並べる
- **判断の軸はアプリの核「クイックに記録できる」**。3品の定食を記録するときのタップ数で比べた:

  | 入口 | 操作 | タップ |
  |---|---|---|
  | 9ボタン | 短押し × 3 | 3 |
  | SearchSheet の中に 🎤 (v0.1 初版の案) | 🔍 → 🎤 → 話す → 記録 | 3 (+ 検索欄の自動フォーカスでキーボードが出たり引っこんだりする) |
  | **ホームの 🔍 の隣に 🎤** | 🎤 → 話す → 記録 | **2** |
  | 🔍 の長押し | 長押し → 話す → 記録 | 2 (ただし見つけてもらえない) |

  - SearchSheet の中に置くと9ボタンより遅くなり、音声を作る意味が無い。**入口は1タップであること**を条件とした
  - 同じ行に置くので9ボタンは下に押し下げられない (失うのは `SegmentedControl` の横幅 約44px のみ)。幅 320px の端末で窮屈でないか、実装時に mobile プリセットのスクショで確認する
  - 長押しは採らない。見つけてもらえない入口だと、KPI で「使われなかった」と出ても理由を切り分けられない
  - 🔍 と 🎤 が並ぶことで、「9ボタンに無いときの道 (打つ / 言う)」として揃う。主役は引き続き9ボタン
- 1語だけ言った場合も確認シートに出す (1件の一覧)。「1件なら検索結果、2件以上なら確認シート」と分けると、同じ操作で画面が変わり学習しにくいため
- **Phase 2: アプリの外の入口**。ウィジェットの 🎤 → `hachibu://speech` で起動と同時に聞き取りを始める / iOS App Shortcuts。ウィジェットの即記録 (pending queue) とは別の仕組み (確認が要るためアプリを開く) なので分けて扱う

### 3.1.1 確認は常に出す (2026-10-02 決定)
- 9ボタンの短押しは「すぐ記録 + 取り消しトースト」だが、**音声はそれに倣わず、全件が層1で確定していても必ず確認シートを通す**
- 理由: 音声認識そのものへの信頼が高くない (変換ミス・聞き取り漏れ・区切りの誤り)。9ボタンは押したものがそのまま入るので誤りの余地が小さいが、音声は「言ったもの」と「入るもの」の間に認識と分解の2段がある
- 「確認で直された割合が低ければ、すぐ記録に切り替える」という案も検討したが採らない。§10 の修正率は**認識と分解の品質を測るため**に使い、確認を省く判断材料にはしない
- そのかわり確認の手間は最小にする: 全件確定なら確認シートで「◯件を記録」を1回押すだけ。記録ボタンは親指の届く下端に置く

### 3.2 使えない環境
- `isRecognitionAvailable()` が false (Android で Google 音声サービスが無い等) → 🎤 を出さない。押してから失敗させない
- 権限を拒否された → 🎤 は出したまま、押したら「マイクの許可が必要です。設定からひらけます。」+ 設定を開くボタン

## 4. 音声認識

### 4.1 ライブラリ
- **`expo-speech-recognition`** (iOS `SFSpeechRecognizer` / Android `SpeechRecognizer` / Web `SpeechRecognition` のラッパー)
- **⚠️ バージョンの罠 (CLAUDE.md 依存ルールの再発防止)**: npm の `latest` は **57.x** で、**SDK 54 に対応するのは `3.1.3`** (dist-tag `sdk-54`)。2026-08-20 の `expo-localization` 事故と同じ構図。
  - サードパーティなので `npx expo install` が SDK 対応版を知らず latest を入れる可能性がある。**`npx expo install expo-speech-recognition@sdk-54` とタグを明示**し、入ったバージョンが 3.1.x であることを `package.json` で確認する
  - config plugin を `app.json` の `plugins` に登録する (権限文言もここで渡す)
  - 追加後に `bun run check:deps`、さらに `expo run:ios` / `expo run:android` で起動確認するまで「動いた」と言わない

### 4.2 権限
| OS | 権限 | 文言 (案) |
|---|---|---|
| iOS | `NSMicrophoneUsageDescription` | 食べたものを声で記録するときに使います。 |
| iOS | `NSSpeechRecognitionUsageDescription` | 話した言葉を文字にして、食べものを探すために使います。 |
| Android | `RECORD_AUDIO` | (OS 標準の文言) |

- 権限は **🎤 を初めて押したとき** に求める。起動時やオンボーディングでは求めない

### 4.3 認識の設定
| 項目 | 値 | 理由 |
|---|---|---|
| `lang` | `ja-JP` (foodRegion が ja のとき) | |
| `interimResults` | true | 話している途中の文字を見せ、聞こえていることを伝える |
| `continuous` | false | 1回の発話で終わる。無音で自動確定 |
| `requiresOnDeviceRecognition` | 端末が対応していれば true | **音声を外に送らない**。対応外の端末では false で動かし、その旨を初回に1度だけ表示 (§4.4) |
| `contextualStrings` (iOS) / `androidIntentOptions` バイアス | ユーザーの ⭐️上位 + Identity ラベル + 料理名辞書の語から最大100語 | 食べものの名前の認識率を上げる (「からあげ」→「空揚げ」等の変換ミス対策の第一手) |
| 最大時間 | 15秒 | 定食1食分には十分。これを超える場合は分けて言ってもらう |

### 4.4 プライバシー
- 端末内認識を既定にする。端末内で認識できない場合のみ OS の認識サーバーを使い、初回に「この端末では、音声は Apple (Google) の認識サービスで文字にします。」と1度だけ出す
- **音声データも認識した文字もアプリは保存しない**。保存するのは診断用の「当てはまらなかった語」だけ (§10)。既存の検索の未ヒット語と同じ扱い

## 5. 分解と照合 (決定的処理)

新規の純粋関数モジュール `utils/speech-parse.ts`。I/O なし・テスト可能。

```ts
parseUtterance(transcript: string, opts: { locale; history }): ParsedItem[]

type ParsedItem = {
  span: string;                 // 聞き取った語 (「からあげ3個」)
  query: string;                // 量の表現を取り除いた語 (「からあげ」)
  amount?: ParsedAmount;        // §5.3
  resolution:
    | { kind: 'entry'; entry: SearchEntry; alternatives: SearchEntry[] }  // 層1で確定
    | { kind: 'maybe'; candidates: SearchEntry[]; vocab: VocabularyMatch[] } // 層2/3止まり
    | { kind: 'unresolved'; categoryHints: BucketKey[] };                // 層4
};
```

### 5.1 区切り
1. 正規化: 既存 `normalize()` を適用する前に、句読点・「、」「。」・スペースを区切り候補として印を付ける
2. **区切り語**: `と` / `、` / `,` / `あと` / `それと` / `それから` / `に` (「ごはんにみそ汁」) / `も` (「サラダも」)
3. **ただし、区切り語で機械的に切らない**。「とんかつ」「トマト」「とろろ」「ところてん」のように語の中に `と` を含む食べものがあるため、次の規則で区切り位置を選ぶ:
   - 区切り候補位置の全組み合わせのうち、**層1で確定する区間が最も多い分け方**を採用する (候補位置は高々数個なので総当たりで十分速い。発話15秒 ≒ 区切り候補 10 以下)
   - 同点なら区間の数が少ない分け方 (= 切りすぎない) を採用する
   - 例: 「からあげとごはん」→ [からあげ][ごはん] (2件とも層1) / 「とんかつ」→ [とんかつ] (「と」「んかつ」は層1にならない)
4. 発話の頭と末尾の決まり文句を捨てる: 「えーと」「あの」「食べた」「を食べました」「です」

### 5.2 照合
- 各区間を既存の `searchEntriesFuzzy` → `getVocabularyMatches` → `getCategoryHints` の順で照合する。**検索シートと同じ層・同じ判定**にして、音声だけ別の当てはめ方をしない
- 層1の1位を確定値とし、2位以降 (最大3件) を `alternatives` として持つ (確認シートで「ほかの候補」として出す)
- 頻度学習 (`history`) をそのまま渡す。同じ「ごはん」でも、ふだん選ぶ種類が上に来る
- `SearchEntry.preset` (ベース + Add-on の組み合わせ。例: ガーリックトースト) に当たった場合は、`resolveLog` に preset の `addons` / `amountValue` を渡す。**確認シートの kcal と記録値が、検索から選んだ場合と一致すること** (2026-10-02 時点で Preset は作業中の変更。実装時に最新の形を確認する)
- §5.3 で取り出した量と preset の `amountValue` が両方ある場合は、話した量を優先する

### 5.3 量
区間の中の量の表現を取り出し、残りを照合に使う。**取り出せない量は無視して既定量にする** (確認シートで直せるため、取り違えるより安全)。

| 表現 | 解釈 | 適用条件 |
|---|---|---|
| 数字 + 助数詞 (`3個` `2本` `2枚` `2切れ` `8皿` `ふたつ`) | 個数 | その Identity の実効 AmountSpec の unit が `piece`/`plate`/`slice`/`cut` のとき、または `altAmount` が個数のとき |
| 数字 + `グラム`/`g` | g | unit が `g` のとき |
| 数字 + `ミリ`/`ml`/`cc` | ml | unit が `ml` のとき |
| `大盛り` `少なめ` `半分` `小` `並` | 量チップ | その Identity の `AmountSpec.chips` の label に一致があるとき。`大盛り` は Add-on (`ご飯大盛り`/`麺大盛り`) が定義されていればそちらを優先 |
| 漢数字・ひらがな数 (`みっつ` `二個`) | 数字に正規化してから上の規則 | |

- unit と合わない量 (「みそ汁 200グラム」で unit が `percent`) は捨てる
- 量の上限は既存 `AmountSpec.max` に従う。超えたら上限で丸めず**捨てる** (聞き間違いの可能性が高い)

### 5.4 受け入れテストの種 (`speech-parse.test.ts`)
| 入力 | 期待 |
|---|---|
| からあげとごはんとみそ汁 | 3件、すべて entry |
| とんかつ定食 | 1件 (区切らない) |
| トマトとレタス | 2件 |

| (空文字) | 0件 → 確認シートに進まず「聞き取れませんでした」 |

## 6. 確認シート (`SpeechLogSheet`)

### 6.1 構成
`BottomSheet` (中に TextInput を持つため `keyboardAware`)。

```
┌──────────────────────────────────┐
│ 「からあげ3個と、ごはん大盛りと、みそ汁」 ✎ │ ← 聞き取った文。✎ で文字を直して再分解 (US-5)
├──────────────────────────────────┤
│ からあげ          3個     280 kcal   ✕ │ ← entry: そのまま記録される
│ ごはん  大盛り    300g    470 kcal   ✕ │
│ みそ汁            1杯      40 kcal   ✕ │
│ ケバブ  もしかして 🍖 脂あり肉魚   …   ✕ │ ← maybe: 候補を選ぶまで記録対象外
├──────────────────────────────────┤
│ 合計 790 kcal                          │
│ [ 言いなおす ]        [ 3件を記録 ]     │
└──────────────────────────────────┘
```

### 6.2 行の状態
| 状態 | 表示 | 記録対象 |
|---|---|---|
| entry | ラベル + 量 + kcal | ○ |
| maybe | 「もしかして」+ 候補チップ (最大3) | × (チップを選ぶと entry になる) |
| unresolved | 聞き取った語 + カテゴリチップ + 「さがす」 | × (チップを選ぶと IdentityLogSheet をそのカテゴリで開く) |

- **maybe と unresolved は記録ボタンの件数に含めない**。「記録した件数」と「画面に見えている件数」がずれないように、ボタン文言に件数を出す (`3件を記録`)
- 記録対象が0件のとき記録ボタンは無効

### 6.3 行の操作
- **行をタップ** → `IdentityLogSheet` を **下書きモード** で開く (種類・トッピング・量をいつもの UI で直せる)。「記録する」の代わりに「なおす」で確認シートに戻る。新しい UI を作らず既存の確認面を再利用する
  - 実装: `openIdentityLogSheet` に `mode: 'draft'` と `onDraftConfirm(resolved)` を追加。下書きモードでは `submitIdentityLog` を呼ばない
- **量だけ直す** → 量の表示をタップで `AmountEditDialog` (既存。AMOUNT_EDIT_DIALOG_SPEC)
- **✕** → 行を外す。取り消しは無し (言いなおせばよい)
- **「ほかの候補」** → entry の行を長押しで `alternatives` を出す (未決 §11 Q3: 長押しで見つけてもらえるか)

### 6.4 ライブプレビュー
- 確認シートが開いている間、記録対象の合計を既存の `updateLivePreview` に流し、カロリーリングで「入るとこうなる」を見せる (IdentityLogSheet と同じ挙動)

### 6.5 コピー (VOICE.md 準拠・案)
| 場面 | 文言 |
|---|---|
| 聞き取り中 | 食べたものを言ってください |
| 聞き取り中の補助 | 「からあげと、ごはん」のように続けて言えます |
| 聞き取れなかった | 聞き取れませんでした。もう一度どうぞ。 |
| 確認シート見出し | これで記録します |
| 層2の見出し | もしかして |
| 層4の見出し | このカテゴリかも (検索と同じ) |
| 記録後トースト | 3件を記録しました ↩ 取り消す |

- 「AIが解析」「自動で計算」のような機能を盛る語は使わない (VOICE.md「期待値を盛らない」)

## 7. まとめて記録

### 7.1 新しい記録 API が要る
現行の `submitIdentityLog` → `pushLog` は1件ずつで、`[log, ...logs]` を **呼び出し時点のクロージャ** から作り、`setLogs` (関数形でない) と `persist` に渡している。**ループで N 回呼ぶと最後の1件しか残らない** (stale closure)。

→ `submitIdentityLogs(resolved: ResolveResult[], opts: { source: 'speech' })` を追加する。
- N 件の `FoodLog` を同じ `timestamp`・同じ `mealSlot` で作り、**1回の `persist`** で保存
- `quickLogHistory` (⭐️タブ / 頻度学習) は N 件分を順に `recordSelection` してから1回で保存。音声で選んだものも9ボタンの学習に効かせる
- `tabUsageCounts` は更新しない (タブを経由していないため。検索経由と同じ扱い)
- `FoodLog` に `source?: 'speech'` を持たせるかは未決 (§11 Q2)

### 7.2 まとめて取り消し
- 現行の `UndoState` は `log: FoodLog` 1件。`logs: FoodLog[]` を持てるよう拡張し、取り消しで N 件をまとめて消す
- トーストは1つだけ出す (「3件を記録しました」)

## 9. ロケール

- **Phase 1: ja のみ**。主辞辞書・料理名辞書が JP 専用 (`getVocabularyMatches` が en-US で空を返す) のため、en-US では層2/3が効かず着地率が下がる
- **Phase 2: en-US**。区切り語に `and` / `,` / `with` / `plus` を追加、量に `two` `a couple of` `cups` 等を追加。US dish vocabulary の整備 (US-food-db-design) が前提
- en-US の Phase 1 では 🎤 を出さない

## 10. 計測 (KPI Layer 1 に相乗り)

`utils/diagnostics.ts` に追加。件数と語だけを保存し、音声・全文は保存しない。

| 記録するもの | 種類 | 読み方 |
|---|---|---|
| 🎤 を押した回数 / 記録まで行った回数 | 二値・件数 | 使われているか |
| 1回あたりの品目数 | 内容 | 「何品もまとめて」が本当に起きているか (1品ばかりなら検索で足りている) |
| 確認シートで直した行 / 外した行の数 | 件数 | 認識と分解の質。**直しが多い = 精度の問題**。確認を省くかどうかの判断には使わない (§3.1.1) |
| 層1に当たらなかった語 | 内容 | 既存の検索未ヒット語と同じリストに `source: 'speech'` で入れる。料理名辞書の育成 (SEARCH_SPEC §5.4.7) にそのまま使える。**変換ミス (空揚げ) もここに出る** |

- `/dev/diagnostics` に音声のセクションを足す

## 13. 受け入れ条件

- [ ] 「からあげと、ごはんと、みそ汁」で3件の entry が出て、まとめて記録できる
- [ ] 「とんかつ」「トマト」が区切られない
- [ ] maybe / unresolved の行は、選ぶまで記録されない。記録ボタンの件数と実際に記録される件数が一致する
- [ ] 確認シートでの修正・除外が記録に反映される
- [ ] N 件記録後、全件がログに残る (最後の1件だけにならない)
- [ ] 取り消しで N 件がまとめて消える
- [ ] 音声で記録した食べものが ⭐️タブの頻度学習に反映される
- [ ] 権限拒否・認識不可の端末で、押してから失敗する導線が無い
- [ ] 音声・全文がどこにも保存されない
- [ ] `bun run check:deps` が通り、iOS / Android のネイティブ起動を確認済み
